## 0. 先纠正派单里的一个前提（重要）

派单说 `out/main/chunk-ZCWQ2IP2.js` 是「对话服务端」。**实测不是**：该文件是
**对话分享（conversation share / publish / import）服务**，其 `loadAllRows()` 只是把
`conversationRowsRangeV4` 当分页读取器用（`docs/_audit/desktop-extract/chunk-ZCWQ2IP2.js` 第 68 行
`limit:he.rowsRangeMaxLimit` / `if(!m.hasMore)break`）。它里面的 CAS 校验（`atLogEpoch`/`atRevision`）
属于**分享快照一致性**，不是对话订阅。

**对话服务端不在 app.asar 里**，而在同一安装目录的 CLI bundle：

| 层 | 文件 | 角色 | 证据 |
|---|---|---|---|
| L1 客户端 | 我们的 Rust / 网页端 / Dart | 调**外层 facade** 方法名 | 见 §1.1 |
| L2 外层 facade | `out/host/chunk-T2GB4I3K.js` @~57,300–68,300 | `RemoteConversationGateway`（`ps()`）：注入 `connectionId`/`clientMode`，剥可信字段 | `function A(t,o){let r={...t};return delete r[yt],delete r.connectionId,delete r.clientMode,delete r.deliveryProfile,delete r.subscriberScope,delete r.workflowRunDeltas,r[yt]=o,r}`（`yt="__zcodeTrustedV4Connection"`） |
| L3 内层 RPC client | `out/host/index.js` @366,723 起 | 把 facade 参数压成 `{topic, connectionId, clientMode, workspace, …}` | `te.request(It.conversationSubscribe,{topic:mt,connectionId:Ge.connectionId,clientMode:Ge.clientMode,…workspace:Qe(g),…})` |
| **L4 服务端** | **`resources/glm/zcode.cjs`** | `v4/conversation/*` 全部 handler + 投影 + 订阅发布器 | `dispatchRequest` @14,960,500；`Sg={conversationSubscribe:"v4/conversation/subscribe",…}` @1,183,309 |

> `resources/glm/.node-bundle-meta.json` 自证来源：`"source": "apps/zcode-cli/packages/cli/dist/zcode.cjs"`。
> 这是被远控方自己跑的进程，故它是**对端权威**；app.asar 内的 schema 与之同构（逐字段核对一致）。

### 1.2 握手（逐步骤，对端权威）

网页端实现是**最直接的 L1 参照**（`Reference_web/3.15.3/assets/index-BGa3KiRe.js` @1,087,400）：

```js

      clientKind: t.clientMode===`desktop-continuous` ? `desktop` : `web`,

```

**步骤 1 — `helloConversationV4()`（无参）**

对端返回（`zcode.cjs` @655,300 附近的 `us()`，即 `createHello`）：

```js
{ kind:"hello", protocolVersion:3, connectionId, clientMode:"desktop-continuous"|"web-remote-replayable",
  deliveryProfile:"continuous"|"replayable", serverTime,
  capabilities:{ nativeDialogs, localTerminal, binaryFrames:false, compression:"none",
                 workspaceHookReview:true, independentPlanState:true, workflowRunDeltas:true },
  auth:{} }
```

- `protocolVersion` 硬编码 **3**（`hF=3` @655,346）。
- **`connectionId` 由对端分配**（facade 构造时 `ht(o.connectionId)` 校验非空且 ≤256 字符，`cs=256`）。
- `deliveryProfile` 与 `clientMode` 必须自洽（schema `superRefine`：
  `clientMode==="desktop-continuous"?"continuous":"replayable"`）。
- `serverTime` 是数字（`mu` = `m.number()`）。

**步骤 2 — `initializeConversationV4(clientHello)`**

facade 侧（`out/host/chunk-T2GB4I3K.js`）：

```js

  let u=Hn.parse(c); if(S!==null&&S!==u.clientId) throw new Error("fault.connection.clientChanged");
```

- **必须先 hello**，否则 `fault.connection.helloRequired`。
- `clientId` **全程不可变**，第二次传入不同值 → `fault.connection.clientChanged`。
- `R = Vn(u)` 把 `clientHello.capabilities` 记下来，决定是否下发 `workflowRun.*` op（见 §2.3）。

clientHello schema（`zcode.cjs` @1,180,275 的 `Fzc`，`.strict()`）：

```
{ kind:"clientHello", protocolVersion:3, clientId:string,
  clientKind?: "desktop"|"web"|"mobileRemote"|"mobileApp",
  appVersion:string,
  capabilities?: { workspaceHookReviewUi?:boolean, workflowRunDeltas?:boolean } }
```

**步骤 3 — `subscribeConversationV4({...scope, sessionId, base?, visibility?})`**

L2 facade（`out/host/chunk-T2GB4I3K.js`）：

```js

  let k=await t.subscribeConversationV4(A(c,u)); …
```

- `Qn(sessionId)` = `conversation/${sessionId}`（`zcode.cjs` @1,183,000 的 `Qn`）。
- `T(c)` = `{connectionId, clientMode, workflowRunDeltas?}`：`terminal-client` 用宿主自己的
  connectionId；`trusted-host-relay` 且带可信标记时用 `relay:${len}:${宿主id}${len}:${客户端id}`。
- `W(c)` = `workspaceIdentity?.trim() || workspacePath`（工作区键）。
- `G(c)` = `{workspacePath, workspaceIdentity?}`。

**L3 实际发出的 subscribe 参数**（`out/host/index.js` @366,723，权威）：

```js

  connectionId: Ge.connectionId,
```

`Qe(g)`（`out/host/index.js` @287,480）= `{workspacePath, workspaceIdentity, remoteSessionId, workspaceKey}`，
其中 `workspaceKey = ge(g) = workspaceIdentity?.trim() || workspacePath`。

服务端 schema（`zcode.cjs` @1,180,000 的 `Knt`，`.strict()`）：

```
{ topic:string, base?:{logEpoch:string, seq:number}, visibility?:"foreground"|"background",
  connectionId:string, clientMode:"desktop-continuous"|"web-remote-replayable",
  workspace?:{workspacePath, workspaceIdentity?, remoteSessionId?, workspaceKey},   // .strict()
  legacyTaskIds?: string[] (≤200), resumeThoughtLevel?:string, workflowRunDeltas?:boolean }
```

> **对端要求的 scope 字段**：`workspace` 是**可选但强烈建议**（冷恢复要用它定位工作区）；
> `connectionId`、`clientMode`、`topic` 是**必填**；`sessionId` **不是** L3 字段（L3 只认 topic）。
> `workspaceKey` 在 `workspace` 对象内**必填**（`workspaceKey:Ou`，非 `.optional()`）。

**步骤 4 — ack**

```js
ack = { subscriptionId:"sub-<logEpoch>-<serial>", mode:"snapshot"|"resume", logEpoch, openTiming? }
```

- `subscriptionId` 由服务端生成：`sub-${this.logEpoch}-${this.nextSubscriptionSerial++}`（`zcode.cjs` @14,577,500）。
- `openTiming`（仅会话订阅；`zcode.cjs` @14,619,200 组装）：
  `{version:1, hostPrepareMs?, cliBootstrapMs?, cliProcessState:"spawned"|"reused", providerRegistrySyncMs,
    taskMetaReadMs, cliRequestMs, cliSessionRestoreMs?, initialFrameEncodeMs,
    sessionRuntimeState:"cold"|"warm", snapshotRowCount}`。
- **初始帧不在 ack 里**：`dispatchRequest` 把初始帧塞进 `postResponseOutbox`，作为**独立的
  `v4/conversation/frame` 通知**在响应之后发出（`zcode.cjs` @14,960,700：
  `this.postResponseOutbox.set(t.id,{messages:i.initialWires.map(a=>({method:NH.conversationFrame,params:a})),commit:i.commit})`）。

**步骤 5 — 后续推送**

`flushStates` 按订阅登记 `{sessionId, topic, subscriptionId, connectionId, deliveryProfile, flushWindowMs}`，
定时器到点调 `reserveFlush` → `emitReservation` → `v4/conversation/frame` 通知。

## 2. 快照与增量

### 2.1 快照形状（`out/main/chunk-OW6EUS2G.js` @615,200 的 `R9`，与 `zcode.cjs` 同构）

```
{
  protocolVersion: 1,
  sessionId, logEpoch, seq, revision,          // 全部必填
  control, availability, inputRouting,
  meta: { title, titleSource },                // 默认 {title:"", titleSource:"default"}
  sharedContextImport?,
  config, modelTransition (nullable, default null),
  usage, queue,
  pendingInteractions: [],
  pendingCommands: [],
  backgroundWorks: [],
  subagents?,
  workflowRuns?,
  goal: …|null,
  plan: …|null,
  workspaceHookAdmission: …|null (default null),
  rows: { window: Row[], totalCount: number, firstRowId: number|null }
}
```

**窗口裁剪语义（易错点）**——`zcode.cjs` @14,570,865 `getWireSnapshotForProfile`：

```js
let o=Enn(n.rows.window,t),                       // Enn = identity（本版不做 profile 行过滤）
    i={...n,rows:{...n.rows,window:o,totalCount:o.length,firstRowId:o[0]?.rowId??null}},
    a=Ha.snapshotTailWindowRows;                  // 60
return o.length<=a?i:{...i,rows:{...i.rows,window:o.slice(-a)}}
```

- `window` 只发**最后 60 行**；
- 但 `totalCount` = **裁剪前**窗口长度，`firstRowId` = **裁剪前**窗口第一行的 rowId；
- 所以 `totalCount > window.length` 且 `firstRowId` 可能**不在** `window` 里 —— 这正是
  「还能往前翻」的判据（客户端 `canLoadOlder = !historyExhausted && firstRowId!=null && totalCount>rows.length`）。
- `rows.window` 里的行按 `rowId` 升序。

### 2.2 帧形状

逻辑帧（schema `$(snapshot, deltas)`，ZI5VUQWA @18,727）：

```
{ topic, subscriptionId, fromSeq, toSeq, sentAt,
  payload: { kind:"snapshot", snapshot } | { kind:"deltas", deltas: Op[] },
  ttft?, ttftRelated? (≤16) }
```

- **snapshot 帧强制 `fromSeq === 0`**（schema `superRefine`：`"snapshot frame must start at seq zero"`），
  且 `snapshot.logEpoch === frame.logEpoch`。
- `toSeq >= fromSeq`。
- 线上信封：`{wireVersion:3, kind:"complete"|"fragment", deliveryKind:"initial"|"online"|"recovery",
  logicalFrameId, logicalFrameOrdinal, topic, subscriptionId, frame|fragment*}`。
  `deliveryKind` 由服务端在 `reserveFrame(...)` 时决定：subscribe 的初始帧 = `"initial"`，
  定时 flush = `"online"`，resync = `"recovery"`。

**op 级过滤（对端真实行为）**：

- `zkr`（`filterConversationDeltasForProfile`，@1,170,245）：
  `e.filter(n => n.op==="row.delta" ? t.streamPaths[n.path] : true)`。
  `streamPaths`：`continuous` = 4 个 path 全开；`replayable`（移动端）= **只有 `text`**。
  ⇒ 移动端**收不到** `inputText` / `output.text` / `summaryText` 的 `row.delta`，这些内容靠
  `row.upserted` 整行覆盖。
- `Enn`（`filterConversationRowsForProfile`）**是恒等函数**（`function Enn(e,t){return[...e]}`），
  即 `desktopOnlyRows` / `toolProgress` 两个 profile 字段在本版**不生效**。
- `subscriberBufferMaxOps=500` / `MaxBytes=1MiB` 溢出 → 该订阅 `resyncRequired=true`，缓冲清空，
  下一次 flush 改发**全量快照**（deliveryKind `"online"`）。

**revision 何时递增**（`deltaBumpsRevision`，`zcode.cjs` @14,470,800）：

```js
case"state.updated": return Ddc.some(t=>e.patch[t]!==void 0);
Ddc = ["control","availability","inputRouting","meta","config","queue",
       "pendingInteractions","backgroundWorks","subagents","goal","plan"]
```

⇒ `state.updated` 只有触及上述键才被认为 bump revision；`row.*` / `pluginUi.*` / `workflowRun.*` 一律不 bump。

### 4.2 `atLogEpoch` / `atSeq` / `atRevision` / `revision`

| 字段 | 生产方 | 消费方（对端） | 是否参与校验 |
|---|---|---|---|
| `revision`（快照内） | 投影 | 命令 CAS 的 `revisionAtDecision` 基准 | **是**（CAS 命令） |
| `atLogEpoch`（rowsRange 返回） | `getRowsRange` | 网页端 `loadOlder`：不匹配就**整批丢弃**（`index-BGa3KiRe.js` @1,136,750）；分享服务跨页一致性 | **是（客户端侧）** |
| `atRevision`（rowsRange 返回） | `getRowsRange` | 仅分享服务 `loadAllRows` 校验 | 订阅路径**否** |
| `atSeq`（rowsRange 返回） | `getRowsRange` | **无**（`grep -b '\.atSeq' zcode.cjs` = 0；网页主包 = 0） | **否** |

网页端 `loadOlder` 的两道校验（原文）：

```js
if(!i||t.atLogEpoch!==i.logEpoch){ Z.warn(`[v4-store] ${this.topic} rows/range 纪元不匹配（${t.atLogEpoch}），整体丢弃`); return }
if(i.rows.window[0]?.rowId!==r) return;          // r = 我们发出去的 beforeRowId
```

**结论**：派单里「只校验 `atLogEpoch` 与 `window[0].rowId`」在**网页端**成立；
在**服务端** `rowsRange` 完全不校验任何 watermark（schema 里就没有 base 字段）。

### 4.3 CAS 冲突怎么重试

- 服务端返回 `{status:"stale", reasonCode, revisionAtDecision}`。
- 客户端应把 `baseRevision` 抬到 `revisionAtDecision`（若 ack 为 `accepted`/`noop`/`duplicate`，则 +1，
  因为该命令会让 revision 前进），**重试一次**。网页/Dart 都是这个算法（`ack_revision_floor`）。
- `baseLogEpoch` 冲突只能靠重新读快照的 `logEpoch`。

## 5. 分页

### 5.1 入参

L1：`conversationRowsRangeV4({...scope, sessionId, beforeRowId?, limit})`
L2：`{...scope, sessionId, clientMode, beforeRowId?, limit}`（`out/host/index.js` @372,376）
L3 schema（`zcode.cjs` @1,183,500 的 `cxr`，**非 strict**）：

```
{ sessionId:string, clientMode?:"desktop-continuous"|"web-remote-replayable",
  beforeRowId?:number, limit:number (1..200) }
```

### 5.2 服务端实现（`zcode.cjs` @14,570,800 `getRowsRange`）

```js
let o=this.projection.getSnapshot(),
    i=Math.max(1,Math.min(t.limit,Ha.rowsRangeMaxLimit)),     // 夹到 1..200
    a=Enn(o.rows.window,wme[n]),                              // profile 过滤（恒等）
    c=t.beforeRowId===void 0?a:a.filter(f=>f.rowId<t.beforeRowId),
    u=c.slice(-i);
return {rows:u, atSeq:o.seq, atRevision:o.revision, atLogEpoch:this.logEpoch, hasMore:c.length>u.length}
```

- `limit` 默认由**客户端**决定：网页 `loadOlder(e=Ie.snapshotTailWindowRows)` = **60**；
  我们 Rust 默认 `ROWS_RANGE_DEFAULT_LIMIT = 60`。服务端**没有默认值**（`limit` 必填）。
- `beforeRowId` 语义：`rowId < beforeRowId`；返回的是这段的**尾部** `limit` 条（升序）。
- 边界标志是 **`hasMore`**，不是 `historyExhausted`。
  `historyExhausted` 是**客户端 UI 层字段**（`conversation.rs:1550` 注释已说明由 UI 写），
  对端线上**不存在**这个字段（`grep 'historyExhausted' zcode.cjs` = 0）。
- `atSeq` / `atRevision` / `atLogEpoch` 只回传，不校验（见 §4.2）。

### 5.3 冷会话

`rowsRange` 会按需 `ensureColdReadyPublisher`（冷恢复会话运行时），失败抛
`V4SubscribeSessionUnavailableError`；超时由宿主侧控制，服务端不设（`conversationQueryTimeoutMs` 未使用）。

### 6.2 服务端状态机（`AttachmentUploadRegistry`，`zcode.cjs` @14,445,400）

key = `uploadKey(connectionId, sessionId, uploadId)`；两个表：`staged` / `committed`。

**begin**

```
committed[key] 存在:
   metadata 完全相同 → {state:"committed", nextChunkIndex, ref}        // 幂等重放/秒传
   metadata 不同     → fault.attachment.beginConflict
staged[key] 存在:
   metadata 相同 → 续传，刷新 TTL，{state:"staging", nextChunkIndex: chunks.length}
   metadata 不同 → fault.attachment.beginConflict
staged.size >= 16            → fault.attachment.tooManyUploads
totalChunks>0 && totalBytes>totalChunks*512KiB → fault.attachment.chunkCountInsufficient
否则 → 新建，{state:"staging", nextChunkIndex:0}
```

**chunk**

```
无 staged → fault.attachment.uploadNotFound
commitPromise 存在 → fault.attachment.commitInProgress
chunkIndex < chunks.length  → 字节必须完全一致，否则 fault.attachment.chunkConflict；
                              一致则返回 {nextChunkIndex: chunks.length}（幂等重放）
chunkIndex > chunks.length  → fault.attachment.chunkGap
chunkIndex >= totalChunks   → fault.attachment.tooManyChunks
空块                        → fault.attachment.emptyChunk
receivedBytes+n > totalBytes→ fault.attachment.totalBytesExceeded
全局 stagedBytes+n > 64MiB  → fault.attachment.stagingCapacityExceeded
成功 → push，刷新 TTL，{nextChunkIndex: chunks.length}
```

**commit**

```
已 committed → {ref}
无 staged    → fault.attachment.uploadNotFound
并发         → 复用同一 promise
chunks.length!==totalChunks || receivedBytes!==totalBytes → fault.attachment.uploadIncomplete
sha256(concat(chunks)) !== checksum → fault.attachment.checksumMismatch
→ host.putSessionAttachment({fileName,mime,bytes}) → {ref}；搬进 committed，TTL 刷新
```

**abort**：若正在 commit 则等它完成；否则删 staged（不存在也不报错）。

### 6.3 `nextChunkIndex` 语义

**永远等于「服务端已连续收到的分块数」**（`chunks.length`），不是「下一块的下标 + 1」之外的任何东西。
因此续传/重放的判据是 `chunkIndex === nextChunkIndex`；`chunkIndex < nextChunkIndex` 是幂等重放
（必须字节一致）；`>` 是 gap。

### 6.4 秒传的比对点（重要修正）

- 秒传判定在 **begin**，比对键是 `(connectionId, sessionId, uploadId)` + **metadata 全等**
  （`fileName`/`mime`/`totalBytes`/`totalChunks`/`checksum` 五项，`sameMetadata` @14,445,100）。
- **没有跨 uploadId 的 sha256 去重**。换一个 `uploadId` 不会命中秒传。
- 真正的落盘去重只可能发生在 `host.putSessionAttachment` 内部（宿主注入，**不在 zcode.cjs 内**）
  —— 该实现**未能证实**。

### 6.5 TTL

| 项 | 值 | 用途 | 证据 |
|---|---|---|---|
| `attachmentUploadTtlMs` | **5 min**（`5*6e4`） | staged 与 committed 条目都在每次 begin/chunk/commit 时刷新 | @656,818；`expiresAt=now+Ha.attachmentUploadTtlMs` |
| 清理周期 | **30 s**（`min(3e4, TTL)`） | `setInterval(()=>pruneExpired(), …)` | @14,606,594 |
| `attachmentUnreferencedTtlMs` | **24 h**（`1440*60*1e3`） | **定义但 0 处使用**（`grep -c 'Ha.attachmentUnreferencedTtlMs'` = 0） | @656,846 |
| 读取缓存 | 30 s / 32 MiB | `attachmentReadCacheTtlMs` / `MaxBytes` | @656,700 |

> 派单里「TTL 5 分钟 / 24 小时」：5 分钟**成立**（上传条目）；24 小时**在 CLI 里未被引用**，
> 不能据此推断服务端会保留 24h。

### 6.6 分片大小

- 协议上限 `attachmentChunkMaxBytes` = **512 KiB**。
- 客户端实际切 **384 KiB**（`ATTACHMENT_CHUNK_BYTES`，Dart/我们 Rust 均如此）；服务端只校验 ≤512KiB。
- `totalChunks ≤ 64`，`totalBytes ≤ 20 MiB`，因此 384KiB×64 = 24MiB > 20MiB，不会撞上限。
- `totalBytes===0` ⇔ `totalChunks===0`（schema `superRefine`：`zero-byte upload must declare zero chunks`）。
