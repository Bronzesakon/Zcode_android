## 1. 入站帧的接收与校验总链（先把链补全）

### 1.1 WS 消息入口：尺寸闸 + JSON 闸 + 追踪

`main-index.js` 381,159–381,506（relay 客户端的 `socket.on("message")`）：

```js
r.on("message",n=>{if(r!==this.socket)return;
 if(ma(n)>kr.maxPhysicalFrameBytes){
   this.options.logger.warn("[web-remote-control] oversize external relay message dropped",
     {bytes:ma(n),maxBytes:kr.maxPhysicalFrameBytes}),
   this.options.onRawTransportFault?.("remote.rpcFrame.envelopeTooLarge");return}
 let o=t0(n);
 if(!o){this.options.logger.warn("[web-remote-control] invalid external relay message");return}

 this.handleMessage(o)})
```

- `ma` = `estimateRawDataBytes`（`main-index.js` 377,6xx）。
- `kr` = **导入名**，`import{... Z as kr ...}from"./chunk-OW6EUS2G.js"`，在 `chunk-OW6EUS2G.js` 内是 `var Ue`（偏移 545,748）：

  ```js
  var Ue={maxPhysicalFrameBytes:Re.maxFrameBytes,maxMessageBytes:16*1024*1024,
           maxFragments:64,assemblyTimeoutMs:3e4,transportIdMaxChars:Re.transportEnvelopeIdMaxChars}
  ```

  `Re.maxFrameBytes:1024*1024`（`chunk-OW6EUS2G.js` 534,064）。⇒ **入站单条 WS 消息硬上限 1 MiB**，超限不解析、直接丢并报 `remote.rpcFrame.envelopeTooLarge`（若当前有桥，则桥被 `markDegraded`，见 §5）。
- `t0` = `parseRelayMessage`（377,0xx–377,4xx）：`ma(e)>kr.maxPhysicalFrameBytes → null`；`JSON.parse` 后要求 `typeof r=="object" && "type" in r`，否则 `null`。
- `logRelayTrace` 体（389,050）：`if(!this.traceRelayMessages)return;` → `logger.info("[web-remote-control][relay-message]",{direction,...})` + 可选 `relayMessageLogger.info`。`traceRelayMessages=!1`（379,037，默认关）。其中 `fS` = `summarizeRelayMessageForTrace`（377,751），对 `type==="data"` 会把 payload 交给 **`hS`** 摘要（见下）。

### 1.4 `vf` 到底是什么（本题最容易搞错的一步）

- `main-index.js` 偏移 **744**：`Lb as vf`（从 `./chunk-OW6EUS2G.js` 导入）。
- `chunk-OW6EUS2G.js` 偏移 **798,585** 的导出表里：`…,qee as Lb,…` ⇒ 外部名 `Lb` = 内部 `qee`。
- `chunk-OW6EUS2G.js` 偏移 **728,113 / 728,128**：

  ```js
  UD=e.union(DD);function qee(t){let n=UD.safeParse(t);return n.success?n.data:null}
  c(qee,"parseWebRemoteControlAppPayload")
  ```

⚠️ **陷阱**：同一个 chunk 里另有一个内部 `function Lb(t,n)`（偏移 473,995）是 **zod 的 `z.object()` 工厂**（`c(Lb,"object")`，并在 zod 命名空间对象里以 `object:()=>Lb` 导出）。它与 `main-index.js` 导入的 `vf` **无关**——`main-index.js` 拿的是导出别名 `Lb`，而导出别名映射到 `qee`。**所以 `vf` 不是 `z.object`，而是「入站帧总校验器」。**

`UD` 是 `e.union(DD)`，**普通 union（非 discriminatedUnion）**，按数组顺序逐个 `safeParse`。`DD` 全 21 臂见 §4.1。

### 1.5 `hS(t)` 记什么（以及有没有别的副作用）

`main-index.js` 377,035，逐字：

```js
function hS(e){if(!e||typeof e!="object"||Array.isArray(e))return{};
 let t=e;return{zcode_type:typeof t.zcode_type=="string"?t.zcode_type:void 0,
  requestId:typeof t.requestId=="string"?t.requestId:void 0,
  bridgeSessionId:typeof t.bridgeSessionId=="string"?t.bridgeSessionId:void 0}}
c(hS,"safePayloadMetadata")
```

- **只**提取 `zcode_type` / `requestId` / `bridgeSessionId` 三个字符串（非法则 `undefined`），**纯函数**。
- 调用点仅两处：丢弃警告（384,998）与 relay 追踪摘要 `fS`（378,028）。**没有任何副作用**：不落盘、不计数、不上报、不改状态。

### 1.6 结论：warn 的副作用 = 零

整条失败路径（384,954）**只产生一条 `logger.warn`**。没有：
- 回执/错误帧（不会回 `app-error` 或任何帧给移动端）；
- 重试、退避、重连；
- 计数器/熔断/限流；
- 遥测上报；
- 状态变更（`state` 仍为 `paired`，`h.error`/`h.failure` 不动）。

⇒ **线上表现是「静默丢弃」**：移动端不会知道自己的帧没被接受（本批与第一批结论一致）。

## 2. `mobile-view-state-update`（最高优先）

### 2.1 该臂的 schema（逐字）

`chunk-OW6EUS2G.js` 偏移 **726,481**（`DD` 数组第 13 个元素）：


- `viewState` **必填**，`deviceInfo` **可选**（键缺省即通过）。
- 本代 zod 别名（第一批已确认）：`e`=`z`，`S`=`z.string()`，`O`=object、`D`=array、`T`=boolean。

### 2.2 `Hf`（viewState）—— 3 键，2 可选

### 2.4 缺陷确认：帧被整帧丢弃，`case` 永不进入

客户端发 `{platform,version,name}`（缺 `updatedAt`）时：

1. `UD.safeParse` 逐臂试：其余 20 臂的 `zcode_type` 字面量都不同，不可能兜住；第 13 臂的 `deviceInfo` 校验失败 ⇒ **整臂失败**；
2. union 失败 ⇒ `qee` 返回 `null` ⇒ `vf(t)` 为假；
3. `handleDataPayload` 走 `logger.warn("[web-remote-control] invalid external relay payload dropped", {zcode_type:"mobile-view-state-update"})` 并 `return`；
4. `onPayload` 不被调用 ⇒ `routePayload`（`main-index.js` 405,108）的 `case"mobile-view-state-update":ho(h,C.viewState,C.deviceInfo)`（**405,422**）**永不执行**；
5. `ho` = `applyMobileViewStateUpdate`（404,331，逐字）：
   ```js
   function ho(h,C,A){h.mobileViewState=C,A&&(h.mobileDeviceInfo=A)}
   ```
   是**全包唯一的 `mobileViewState` 写入者** ⇒ `h.mobileViewState` **在整个会话里恒为 `undefined`**（运行时对象字面量 408,700–409,000 里根本没有初始化 `mobileViewState`/`mobileDeviceInfo` 键）。

**唯一写入者**这一条的旁证：渲染层有 6 处 `p/d/f.updateMobileViewState(...)` 调用（`styles-CSpM3qgc.js:510` 偏移 4,289,212 / 4,304,966 / 4,320,506 / 4,320,631、`:1184` 偏移 4,831,873 / 4,831,958），但**全包 21,920 个文件里没有该属性的任何定义**，且每处都有前置守卫（`if(!p.updateMobileViewState)return;`、`if(!f?.updateMobileViewState||!ln)return;`）。⇒ ⚠️ 推测：这些调用点在当前构建里不生效（死路径/为另一构建预留）。因此**入站帧是唯一生产者**。

### 2.6 最小修法（含可验证判据）

**够不够只补 `updatedAt`？——够，而且是唯一缺口。**

- 该臂只有两个子对象：`viewState:Hf`（必填）与 `deviceInfo:MD`（可选）。
- `Hf`：`activeWorkspaceKey`/`activeTaskId` 可选、`updatedAt` 必填 → 我们已发 `updatedAt`（`zemote_client.rs:2473`）✔
- `MD`：`platform`/`version`/`name` 我们已发 ✔；8 个可选键全缺无害；**唯一缺口就是 `updatedAt`**。
- 其余 20 臂的 `zcode_type` 字面量都不同，不可能兜住 ⇒ 修好 `updatedAt` 后必然命中第 13 臂。

⇒ **最小形状（充分且必要）**：

```json
{"zcode_type":"mobile-view-state-update",
 "viewState":{"activeWorkspaceKey":"<k>","activeTaskId":"<t>","updatedAt":<finite number>},
 "deviceInfo":{"platform":"<p>","version":"<v>","name":"<n>","updatedAt":<finite number>}}
```

**两种实现选项**（推荐 A）：

- **A（推荐，改动最小、风险最低）**：**只在 `mobile_view_state_update_payload` 调用点**给 `deviceInfo` 补 `updatedAt`（例如 `device_info` 的序列化结果上再 `insert("updatedAt", json!(now_ms))`），`device_info::DeviceInfo` 与 `auth_init.meta` **不动**。
  理由：`relay_client.rs:555` 是 `"meta": self.device_info.clone()` —— 若直接给 `DeviceInfo` 加字段，**`auth_init.meta` 也会多出 `updatedAt`**，而 relay 的 `meta` 校验在**服务端**（桌面端只发不校验；桌面自己的 meta 是 3 键，`main-index.js` 407,953 `meta:{platform:process.platform,version:e.appVersion,name:e.deviceName}`），本仓无法静态证伪「服务端是否 `.strict()`」。修 view-state 不该顺带冒配对失败的风险。
- **B（形状最干净，但需真机回验）**：给 `DeviceInfo` 加 `updatedAt: i64` 字段，接受 `auth_init.meta` 同步多一键；若配对仍成功即证明服务端 meta 非 strict。

顺带：`device_info.rs:89` 的注释「线上字段名（**已冻结，不可改**）：`platform`、`version`、`name`」**与对端事实冲突**（对端要求 4 键，第 4 键是 `updatedAt`）。至少应改成「relay `auth_init.meta` 用这 3 键；`mobile-view-state-update.deviceInfo` 还必须带 `updatedAt`」，否则后续维护者会再次踩同一个坑。

**可验证判据（三层）**：

1. **静态判据（本机可验，已通过）**：`MD` 12 键里没有 `.optional()` 的只有 `platform`/`version`/`name`/`updatedAt`；`Hf` 里没有 `.optional()` 的只有 `updatedAt`。因此「3+1 键」是能过 `UD.safeParse` 的最小 `deviceInfo`。
2. **端到端判据（需真机/真桌面）**：修后重跑一次配对并触发一次 view-state 更新，观察
   - 桌面日志**不再**出现 `"[web-remote-control] invalid external relay payload dropped"` 且 `zcode_type:"mobile-view-state-update"`；
   - 桌面侧边栏出现 `data-mobile-active-task="true"` 与 tooltip「手机正在操作此任务」；
   - 桌面状态推送里 `mobileViewState` 非 `undefined`。
3. **反证判据**：只补 `viewState`（我们本来就对）或只补 `deviceInfo` 的其它可选键，桌面端仍会打出**同一句** warn ⇒ 失败点确定在 `deviceInfo.updatedAt`。

### 6.2 结论：修 D1 的最小改动面

**只改一处**：`rust/crates/protocol/src/zemote_client.rs:2481-2486`（`mobile_view_state_update_payload` 的 `deviceInfo` 构造）——在 `serde_json::to_value(device_info)` 的结果上补 `updatedAt`（值用已有的 `now_ms` 形参，语义与 `viewState.updatedAt` 一致）。

- **不要**改 `device_info.rs:98` 的 `DeviceInfo`（会连带改 `relay_client.rs:555` 的 `auth_init.meta`）。
- **要**改 `device_info.rs:89` 的注释（D2），把「已冻结，不可改」改成按用途分列的事实。
- 需要同步更新的既有断言：`zemote_client.rs:2897` 的 `"deviceInfo": {"platform": "android", "version": "0.5.3", "name": "zemote"}`、`:3163-3165` 的三条 `assert_eq!`——它们会把「3 键」钉死，不改就会红。

## 7. 仍未证实 / 需要抓包

1. **服务端（relay）对 `auth_init.meta` 是否 `.strict()`** —— 决定 §2.6 选项 B 是否安全。桌面端只发不校验（`main-index.js` 407,953），本仓无服务端代码。**需要**：抓一次配对握手，或在 `auth_init.meta` 里故意多带一个字段看服务端是否 `WRONG_PARAM`/`AUTH_FAILED`。
2. **`mobileViewState` 丢失的真实用户可见后果的严重度** —— §2.5 的 6/7 两项是静态推断（渲染层读 `Gt.mobileViewState`），**没有真机截图**证明「修好后标记确实出现」。**需要**：真机（或本机跑桌面端 + 我们的客户端）在修 D1 前后各截一次侧边栏。
3. **渲染层 `updateMobileViewState` 是否真为死路径** —— 全包 21,920 文件 grep 无定义，但属性可能由运行时动态拼装（未证实）。**需要**：在渲染层断点/注入探针确认这些调用是否可达。若可达，则「入站帧是唯一写入者」需要修正。
4. **`mobile-diagnostic` 是否存在日志级限流** —— 已确认应用层无限流（`main-index.js` 无任何包装），但**桌面 logger 自身**（`e.logger`，另一个模块）是否有采样/落盘上限未查。**需要**：查 logger 实现，或抓包实测高频 diagnostic 的桌面日志行为。
5. **`telemetry-report` 是否真的被上报** —— 静态链是 `reportRendererTelemetryEvent?.(C.event)` → `go.reportEvent`；但 `reportRendererTelemetryEvent` 是**可选调用**（`?.`），且 `go` 的上报还依赖 `loadUserId`/`loadAuthorization`（未登录可能丢）。**需要**：抓一次移动端 `session_create` 后的出网请求，确认事件真的带 `client_kind:"mobile"` 到达 ZCode 端点。
6. **`app-error` 入站是否在别处（host 进程）被处理** —— 已确认 `routePayload` 只在 `out/main/index.js`（`host-index.js` 无 `routePayload`、无 `case"mobile-view-state-update"`/`"mobile-diagnostic"`），但 host 侧是否另有 relay 通路未穷举。**需要**：`host-index.js` 的 relay 通路专项（可能属别篇范围）。
7. **`workspace-list-updated` 的去重签名是否含 `mobileViewState`** —— `buildWorkspaceListPushSignature`（399,510）的 `D(h)` 只对 `workspaces`/`tasks` 的选定字段做 `JSON.stringify` 排序比较，**不含** `activeWorkspaceKey`/`activeTaskId` ⇒ 推测「手机视图变化不会触发列表推送」。⚠️ 推测，未逐字段核对 `D` 的字段集（本文件未展开，属另一篇范围）。
