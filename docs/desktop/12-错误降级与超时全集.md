## 0. 结论速览

1. **`rS` 失败原因枚举确为 11 个值，桌面端与网页端逐字一致**。但桌面端 `out/main` 只**实际发出**其中 5 个
   （`session-conflict` / `workspace-closed` / `desktop-disconnected` / `unsupported-action` / `unexpected-error`）；
   其余 6 个桌面端无发起点，其中 `desktop-bootstrap-timeout` / `relay-unavailable` / `invalid-mobile-connection` /
   `session-not-found` / `session-expired` 由客户端发出，`connection-recovery-timeout` 全构建无任何发起点。
2. **`bridge-degraded.reason` 4 个值里，桌面端只发 `rpc-transport-fault`**；`rpc-frame-gap` /
   `buffer-overflow` / `buffer-timeout` 只有 schema，无发起点（全包 21,920 文件复核）。
3. **relay 顶层 `error.code` 桌面端只识别 4 个**：`KICKED` / `AUTH_FAILED` / `INTERNAL` / `WRONG_PARAM`，
   其余一律走 `enterError`（**终态**）。**`DEVICE_OFFLINE` 在桌面端全包 0 命中**——它只存在于客户端。
   桌面端对 `KICKED` 的处理是「关 socket → 1 s 后重连」，**不是终态**；`setState("kicked")` 全包 0 次。
4. **fault reasonCode 全集 = 36（`remote.rpcFrame.*`）+ 23（`proto.*`）+ 51（`fault.*`）= 110 个字符串常量**。
   其中 `remote.rpcFrame.*` 里 **25 个 terminal、1 个非终态**（`identityMismatch`），另 10 个是编码/配置错误（抛异常，桥起不来）。
5. **`subscriberBufferMaxOps`(500) / `subscriberBufferMaxBytes`(1 MiB) / `eventRetentionPerSession`(2000) /
   `idempotencyTablePerSession`(512) 在桌面端只有常量表声明，全包无读取点**——对端 3.15.3 不执行这四条。
   真正生效的背压是 ack'd relay 的 1 MiB 高水位 / 256 KiB 低水位 / 8 MiB replay 缓冲 / 45 s 宽限。

### 2.3 4 值逐个：触发 / 恢复

| 值 | 触发条件 | 桌面端是否发出 | 恢复条件 / 客户端处置 |
|---|---|---|---|
| `rpc-transport-fault` | ack'd relay 协议 `enterDegraded()` 的**任意**原因（`onDegraded` 回调） | ✅ 唯一实际发出值 | 客户端 `markDegraded()` + 走 `A()` 恢复：relay 重连 → 重新 bootstrap（`index-BGa3KiRe.js` @6,578,134 收到帧；@6,577,262 `A` 恢复函数） |
| `rpc-frame-gap` | schema 声明；桌面端无发起点 | ❌ 仅 schema | 语义上应由帧序号缺口触发；⚠️ 未能证实由谁产生 |
| `buffer-overflow` | schema 声明；桌面端无发起点 | ❌ 仅 schema | ⚠️ 未能证实 |
| `buffer-timeout` | schema 声明；桌面端无发起点 | ❌ 仅 schema | ⚠️ 未能证实 |

schema 里成立；但**桌面端只产生第 1 个**，后 3 个在本构建里是死枚举值。若要在客户端做分支，
可按 4 值实现（向后兼容），但不能把后 3 个当作对端一定会发。

### 2.4 降级后桌面端做什么

`I()` 只做三件事：置 `C.degraded=!0`、打日志、发一帧 `bridge-degraded`。
**不关 socket、不释放 host attachment、不重置 `bridgeSessionId`。** 后续所有
`sendFrame` 在 `q.degraded` 为真时直接返回 `false`（`main-index.js` @401,922 的 `sendFrame` 闭包：
`if(!q.readyAnnounced||q.degraded)return!1`），即桥进入只读/停写状态，等移动端发起恢复。

### 3.4 全集的结论

relay 可能下发的 code 全集 = **`KICKED` / `DEVICE_OFFLINE` / `AUTH_FAILED` / `WRONG_PARAM` / `INTERNAL`**（5 个），
外加「未知 code」兜底。两端语义**不对称**：

- `DEVICE_OFFLINE`：只有客户端认；桌面端（设备）落到默认分支 ⇒ **终态**。角色上合理（设备不会被告知
  「设备离线」），但意味着**桌面端对未知 code 的容错为零**。
- `KICKED`：客户端终态，桌面端重连。
- `AUTH_FAILED`：桌面端有一次「持久凭据失效 → 重新注册」的自愈；客户端直接终态。
- `INTERNAL`：两端都按可恢复处理。
- `WRONG_PARAM`：桌面端在已配对时**只报错不动作**（可能造成「报错但状态不变」的悬挂），客户端终态。

**BRIEF 的「`DEVICE_OFFLINE` 15 s 宽限」在桌面端不成立**，只在客户端成立。此处以桌面端为准并记录冲突。

## 6. 限流与背压

### 6.1 ack'd relay 协议（真正生效的一层）

来源 `out/main/chunk-JS2T33SG.js`。

```js
// @7,203
var m={saturationHighWaterMarkBytes:1024*1024,      // 1 MiB
       saturationLowWaterMarkBytes:256*1024,        // 256 KiB
       replayBufferMaxBytes:8*1024*1024,            // 8 MiB
       replayBufferGraceMs:45e3,                    // 45 s
       assemblyTimeoutMs:g.assemblyTimeoutMs}       // 30 s
```

| 机制 | 阈值 | 超限/跨界行为 | 坐标 |
|---|---|---|---|
| 高水位（出站未确认字节） | > **1 MiB** | 置 `saturated=true`，`onSaturated` → 向 host 发 `sendFlowState("saturated")`（host 停止推送） | @7,203；`main-index.js` @402,076 |
| 低水位 | ≤ **256 KiB** | 置 `saturated=false`，`onDrained` → `sendFlowState("drained")` | 同上；@402,152 |
| replay 缓冲上限 | > **8 MiB** | **终态降级**：`remote.rpcFrame.replayBufferExceeded` ⇒ `bridge-degraded`（不清空重发，直接废桥） | @11,590 |

## 7. 恢复策略

### 7.1 终态 vs 可恢复

| 层次 | 终态（不再自愈） | 可恢复（有明确恢复路径） |
|---|---|---|
| relay 连接 | 未知 `error.code` / `AUTH_FAILED`（非持久模式）/ `WRONG_PARAM`（非 paired）⇒ `enterError`（`terminalClose=!0`） | `KICKED`（重连）、`INTERNAL`（回 waiting 或重连）、`AUTH_FAILED`+持久凭据（重注册）、心跳 ack 超时（重连）、socket 关闭（重连） |
| workspace 桥 | `session-conflict` / `workspace-closed` / `desktop-disconnected` / `unsupported-action` / `unexpected-error` ⇒ `preserveWindowRuntimeFailure`（`status="error"`，dispose transport） | `bridge-degraded` ⇒ 桥 `degraded=true`，等移动端发 `workspace-reconnect-request` |
| ack'd relay 传输 | 25 个 terminal fault ⇒ 废传输 + `bridge-degraded` | `identityMismatch` 只丢单帧 |
| host 订阅 | `fault.connection.closed`（该连接） | `runtimeRestarted` / `transportReplaced` / `resyncGenerationMismatch` / `initialFrameStagingOverflow` ⇒ 重新 `subscribe`/`resync` |
| 单请求 | —— | 所有 `proto.*` / `fault.*` 业务错误都是单请求失败，不影响连接 |

### 7.2 各路径

1. **relay 掉线**：socket `close` →（非 `terminalClose`/非手动）→ `scheduleReconnect(1,000 ms)`；
   `paired` 期间掉线还会在状态切到 `reconnecting` 时把活跃桥标 degraded（客户端侧 `_onRelayState`，
   我们的 Rust 对应 `conversation_transport.rs` 的 `BridgeDegraded` 路径）。
2. **心跳 ack 超时**：`reconnectAfterStaleWaiting(jitter)` → 关 socket + 重连。
3. **stale waiting**：`paired` 后 relay 又回 `waiting` 且 `staleWaitingCount` 增长 ⇒ 15 s 后强制重连；
   第二次仍 `waiting` 立即重连。
4. **桥降级**：桌面发 `bridge-degraded`（`rpc-transport-fault`）；客户端 `markDegraded()` → `A()`：
   `recoverConnection()`（relay 重连）→ 重新 bootstrap（`O?.()`）→ 失败则 `recoverInBackground()`。
5. **桥终态**：桌面发 `app-error` / `workspace-bridge-error`（带 `rS`）；客户端 `E()` = 终态失败 UI
   （`K9`），销毁 relay/transport/桥，不自动重试。
6. **需要用户重新配对**：只有 `invalid-mobile-connection`（客户端终态）与桌面端 `AUTH_FAILED`
   持久凭据失效（桌面会自动重注册一次，重注册失败即终态）会走到「重新扫码/重新配对」。
   `bridge-degraded` **不需要**重新配对，只需重新 bootstrap。

## 9. 仍未证实 / 需要抓包

1. **`connection-recovery-timeout` 的触发点**：11 个 rS 里唯一**没有任何发起点**的一个——它只出现在
   客户端 i18n 失败文案表（@6,539,816 / @6,543,798 / @6,556,201）与 `D6n` 的接受列表（@6,555,900），
   没有 `q9('connection-recovery-timeout', …)` 的构造。需要抓包或 relay 服务端证据。
2. **`rpc-frame-gap` / `buffer-overflow` / `buffer-timeout` 由谁产生**：桌面端 3.15.3 全包只有 schema。
   可能是旧版本遗留、或留给未来版本；需要一份真实 `bridge-degraded` 抓包确认线上是否出现。
3. **`DEVICE_OFFLINE` 的服务端语义**：桌面端 0 命中、客户端有 15 s 宽限。relay 在什么条件下发它、
   是否只发给移动端，未证实。
4. **`subscriberBufferMaxOps/Bytes`、`eventRetentionPerSession`、`idempotencyTablePerSession`
   是否由 relay 云端执行**：桌面端本进程无读取点，但 relay 可能按同一份常量表限流。
   需要 relay 侧行为抓包或服务端代码。
5. **`conversationQueryTimeoutMs` 等「只声明不执行」的常量是否在 host 侧以别的名字生效**：
   本报告只证明了字面量无读取点，未排除值被内联或通过其它对象访问。
6. **`KICKED` 桌面端重连后是否会形成 loop**：`setState("kicked")` 为 0 次，`ET` 的 `kicked` 分支
   在本构建看似死代码。需要真机抓包确认「另一控制端抢占」后桌面端的实际行为（是一直重连抢回，
   还是最终被 relay 拒绝）。
7. **`WRONG_PARAM` 在 `paired` 状态只报错不动作**是否会造成悬挂：静态读码如此，需真机验证。
8. **`bridge-degraded` 是否带 `seq/expectedSeq/droppedCount`**：schema 有这三个可选字段，
   但唯一发起点 `I()` 只发 `bridgeSessionId/bridgeGeneration/recoveryId/reason`，从不填这三个。
   需抓包确认线上是否出现过。
9. **`remote.rpcFrame.*` 的 `terminal` 值在线上是否可观测**：它只进日志，不上线；
   要验证得拿到桌面端日志。
