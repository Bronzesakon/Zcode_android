## 0. 结论摘要（先回答派单里的两个关键问题）

| # | 问题 | 答案 |
|---|---|---|
| A | 客户端 scope 里只有 `workspacePath`（值其实是 workspaceKey）、没有 `workspaceIdentity` 时，桌面端能否正确定位工作区？ | **对 `workspace-bridge-open` 帧：能——但前提是 key 放在 `workspaceKey` 字段里。** 桌面端**根本不读** `workspacePath` / `workspaceIdentity`（这两个键连 schema 里都没有）。它只做一件事：`M(h).find(Se => Ve(Se) === C.workspaceKey)`，即拿本窗口的工作区列表按 **key** 精确匹配。所以「只有 path 没有 identity」不是问题；**问题是 key 必须叫 `workspaceKey` 且值必须算对**。缺 `workspaceKey` ⇒ 帧校验失败 ⇒ 静默丢弃（连 error 都不回）。值算错 ⇒ `workspace-bridge-error`，`reason:"unexpected-error"`。**不会开错工作区**——桌面端从不按路径反查，找不到就失败。 |

### 1.3 关于「客户端 scope 只有 workspacePath、没有 workspaceIdentity」

分两种情况，结论不同：

**(a) 发的是 `workspace-bridge-open` 帧。**
桌面端只用 `workspaceKey` 定位，`workspacePath` / `workspaceIdentity` 完全不参与。因此：

- 只要 key 值正确 ⇒ **能正确定位**，与有没有 identity 无关。
- 如果客户端把 key 塞进一个**名为 `workspacePath` 的字段**而没给 `workspaceKey` ⇒ **必然失败**（缺必填项，静默丢弃）。
- 如果 key 算错（例如桌面端该工作区有 `workspaceIdentity`，客户端却用了 raw path）⇒ `.find` 落空 ⇒ 返回 `workspace-bridge-error`。
- **不存在"开错工作区"**：查找是 `===` 精确匹配，没有路径前缀/归一化/模糊回退，找不到就报错。

**(b) 发的是 `conversation` 通道 RPC（`zcode-agent` 通道）的 scope。**
见 §7，那里 `workspacePath` 是真实路径，不能放 key。

### 2.3 `workspaceIdentity` 什么时候为 null

**线上永远不会是 `null`，只会"缺席"。** 三处证据一致：

1. 生产者用 `...e.workspaceIdentity?{workspaceIdentity:e.workspaceIdentity}:{}` —— 假值（`undefined` / `null` / `""`）时**整个键不出现**。
2. schema 是 `S.optional()`，而 `S = e.string().trim().min(1)`：**写 `""` 或纯空白会校验失败**，只能省略。
3. `remote` 工作区的变体（`zD` 的 remote 臂）才把 `workspaceIdentity` 列为**必填**，`local` 臂根本没有这个键。

所以「`workspaceIdentity` 为 null」在协议层的等价说法是：**该工作区是纯本地工作区，key 就是 `workspacePath`。**

另一个变体 `$Jn`（@6,260,935）只产出「远程且已连接」的子集，用于另一条 effect：

## 4. bridge 生命周期状态机

### 4.1 桌面端持有的状态

`out/main/index.js` 里每个窗口的运行期对象 `h`（`ge`）持有：

| 字段 | 含义 |
|---|---|
| `h.currentBridge` | 当前桥对象 `q`；`undefined` = 无桥 |
| `q.bridgeSessionId` / `q.bridgeGeneration` / `q.recoveryId` | **从 open 帧原样抄下**，此后只用于回显 |
| `q.kind` / `q.workspaceKey` / `q.workspacePath` / `q.workspaceIdentity` / `q.remoteSessionId` | 从**桌面端自己的工作区列表**里取（不是从帧里取） |
| `q.initialTaskId` | 从 open 帧的 `taskId` 取 |
| `q.readyAnnounced` | ready 发出后置真，之后才允许发 rpc-frame |
| `q.degraded` | 降级后置真，此后拒收/拒发 rpc-frame |
| `q.hostProtocol` / `q.relayProtocol` / `q.disposeBridge` | 桥的两层协议栈 |

`h.status` 取值：`starting` → `connecting` → `active`（`mobileConnected` 时）/ `running`。

### 4.4 `bridgeSessionId` / `bridgeGeneration` / `recoveryId` 的产生与失效

**三者全部由客户端产生，桌面端只做三件事：存下来、回显、在 error/degraded 里带出。桌面端从不生成、从不递增、从不校验。**

| 量 | 谁生成 | 规则 | 桌面端行为 |
|---|---|---|---|
| `bridgeSessionId` | **客户端** | 每次 open（含恢复重开）都换一个新的 | 存进 `q.bridgeSessionId`；ready/error/degraded 回显；`h.currentBridge.bridgeSessionId === C.bridgeSessionId` 用于置 `readyAnnounced`；`failRemoteSession` 用它做关联 |
| `bridgeGeneration` | **客户端** | 客户端自增计数 | 仅回显；`N.bridgeGeneration===C.bridgeGeneration` 参与 `readyAnnounced` 判定 |
| `recoveryId` | **客户端** | 每次恢复尝试新生成一个（web 端 `l=X9(\`recovery\`)`）；廉价恢复成功则清空不下发 | 仅回显 |

客户端侧权威实现（web 参考实现，与桌面端同版本）：

- `Reference_web/3.15.3/assets/index-BGa3KiRe.js` @6,462,350 附近：

  —— `n` 新 id、`r=++u` 自增、`l` 一次性 recoveryId、**匹配器只校验 `bridgeSessionId`**。
- 恢复入口 @6,459,400 附近：

**失效规则：**

### 4.5 `recovery` 流程

**`bridge-recovered` 这个帧在 3.15.3 不存在。** `DD` 联合共 21 个 arm（@725,057–728,113），逐个枚举：`telemetry-report`、`bootstrap-request/-response`、`workspace-list-request/-response/-updated`、`workspace-bridge-open/-ready/-error`、`workspace-reconnect-request`、`workspace-reconnect-response`（成功/失败两个 arm）、`mobile-view-state-update`、`platform-request`、`platform-response`（成功/失败）、`xr`（rpc-frame）、`Dg`（rpc-frame-ack）、`bridge-degraded`、`app-error`、`mobile-diagnostic`。**没有 `bridge-recovered`。**

**(1) `workspace-reconnect-request` → `workspace-reconnect-response`**

## 5. 同一工作区多次开桥：复用还是新开？

**新开，旧桥被拆。没有复用、没有引用计数。**

`te` 的第一件事就是 `w(h)`（@400,202 第二行），`w` = `disposeRuntimeBridgeResources`（@392,632）：

```js
function w(h){let C=h.currentBridge;if(C){C.disposeBridge?.(),C.disposeBridge=void 0,C.relayProtocol?.dispose(),C.relayProtocol=void 0;try{C.hostProtocol?.disconnect()}catch{}C.attachmentId&&e.releaseWorkspaceHostAttachment(C.attachmentId),h.currentBridge=void 0}}
```

拆的内容：rpc-frame 协议栈、relay 协议栈、host 端口连接、host attachment 引用。**注意 `w(h)` 不区分工作区**——即使新 open 的是另一个工作区，旧桥也一并拆掉（一个窗口同时只有一条桥）。

随后：

```js
let q={bridgeSessionId:C.bridgeSessionId, …}; h.currentBridge=q;
…
re=await e.attachWorkspaceHost(…), !b(h,q)&&(e.releaseWorkspaceHostAttachment(re.attachmentId),re=void 0,new Error("Workspace bridge request was superseded."));
```

`b` = `isCurrentBridgeRuntime`（@392,933）：`function b(h,C){return t.get(h.windowId)===h&&h.currentBridge===C}` —— **对象身份比较**。它防的是「open A 还在 await，open B 已经插进来」的竞态：A 完成后发现 `currentBridge !== q_A`，就释放自己刚拿到的 attachment 并抛 `Workspace bridge request was superseded.`（映射成 `unexpected-error`）。

**`bridgeGeneration` 在这里的作用：零。** 它只是被抄进 `q` 再回显；竞态判定用的是对象身份，不是世代号。

**对客户端的实践含义：**

- 对同一工作区重复 open 是安全的（会得到一条新桥 + 新 `bridgeSessionId`），但**旧桥上的所有 rpc-frame 在途/重放全部作废**。
- 不要并发 open 两个不同工作区并期望都活着——后一个会拆掉前一个。
- 恢复重开时务必换新的 `bridgeSessionId`（web 端与我们的 Rust 都这么做），否则桌面端 `q` 里的旧 id 会和客户端新状态错位。

## 6. `taskId` 的作用：带与不带

`taskId` 在桌面端**只影响展示层，不影响桥的建立**。

| 用途 | 坐标 | 说明 |
|---|---|---|
| 存进 `q.initialTaskId` | `out/main/index.js` @400,958 | `initialTaskId:C.taskId` |
| 传给 `attachWorkspaceHost` | @401,362 | `{…,initialTaskId:C.taskId,kind:A.kind}` |
| 运行期状态回显给渲染层 | @394,230 `L(h)` | `initialTaskId:h.currentBridge?.initialTaskId??h.initialTaskId` |
| `workspace-list-response` 的 `activeTaskId` | @398,995 `W(h)` | `h.mobileViewState?.activeTaskId ?? h.currentBridge?.initialTaskId ?? A?.activeTaskId` |
| 遥测 `entryKind` | @~401,4xx | `entryKind:C.taskId?"task":"home"` |

**关键：`initialTaskId` 根本没有送进 host 进程。** `attachWorkspaceHost` 的实现（`out/main/index.js` @629,082）：


- `kind === "local"` → `return o(l)`，**整个 `u`（含 `initialTaskId`、`workspacePath`、`workspaceIdentity`）被完全忽略**，只用了 `windowId`。
- `kind === "remote"` → `attachRemoteWorkspaceSessionHost` 的参数里**没有** `initialTaskId`。

⇒ **带 `taskId` 与不带 `taskId`，对桌面端「打开哪个工作区 / 哪个 host」毫无区别。** 差别只有：移动端在桌面端 UI 上被记为「正在看某个任务」，以及 `workspace-list` 里的 `activeTaskId`。真正的「打开哪个对话」由客户端自己发 `conversationSubscribe({sessionId})` 决定。

顺带一条：`attachRemoteWorkspaceSessionHost` 里的 `p = m || u.workspacePath` 再次印证 key 规则（`m` 已经是 trim 过的 identity）。

### 7.1 桥打开之后，RPC 是怎么落到 host 的

`out/host/index.js` @16,662,217（`Zi` 的 `resolveScope`）：

### 8.3 一句话给父对话

- **`workspace-bridge-open` 不用改**：我们发的 `workspaceKey` 形状与桌面端 schema 完全一致。
- **`conversation` 的 scope 必须改**（A1/A2）：`workspacePath` 要真实路径、`workspaceIdentity` 要单独给。这不是"可选优化"，而是远程工作区直接不可用。
- **`WorkspaceProjection`（A3）是另一个独立 bug**：它把桌面端 `workspaces[i]` 全丢光了，导致宿主要拿真实路径也无处可取。
- **R4/R9 的 trim 语义**要补：`workspaceIdentity?.trim() || workspacePath`，而不是 `?? `。
