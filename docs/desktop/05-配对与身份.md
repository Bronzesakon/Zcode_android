## 1. 配对链接 / 二维码

### 1.1 调用链（谁生成、谁渲染）

桌面端**只有 main 进程生成配对 URL**，renderer 只负责把 main 给的字符串画成二维码 / 复制按钮。

```
main-index.js  bS() 工厂（createWebRemoteControlManager）
  └─ start(h, C)                                    @407110
       ├─ authStorageProvider.load()                @407522  → 命中则 mode="persisted"
       │                                            未命中 → mode="register"，现场造口令
       ├─ 构造 relay 客户端 Bm = m({relayWsUrl, deviceMid, auth, meta, authProvider, …})
       ├─ await Uc  ← 「QR-ready」闸门（waiting_terminal 或 paired 才放行；c0=30 s 超时）  @407721

       └─ let fn = TT(ir, q, C.theme)               @409712  ← 生成 URL（q = remoteUrl）
```

`TT` 是 `createQrUrl`，它只是把参数转发给共享 chunk 里的 `Xf`：

**原文（`main-index.js` @406820（`TT` 定义）；调用点 @409712）：**


### 1.2 权威 URL 生成函数（逐字）

**原文（`chunk-OW6EUS2G.js` @780843）：**

```js
function ace({baseUrl:t,deviceSid:n,passHash:r,timestamp:a,deviceMid:o,deviceName:i,appVersion:s,theme:l}){
  let p=new URL(t);
  return p.searchParams.set("sid",n),
         p.searchParams.set("hash",r),
         p.searchParams.set("t",String(a)),
         o?.trim()&&p.searchParams.set("mid",o),
         i?.trim()&&p.searchParams.set("name",i),
         s?.trim()&&p.searchParams.set("app_version",s),
         p.toString()

c(ace,"buildWebRemoteControlExternalQrUrl")
```

**权威形态（参数顺序即写入顺序）：**

```
<baseUrl>?sid=<deviceSid>&hash=<passHash>&t=<Date.now() 毫秒>&mid=<deviceMid>&name=<deviceName>&app_version=<桌面端 appVersion>
```

### 1.3 参数表

| 参数 | 写入条件 | 来源 | 语义 | 必需 |
|---|---|---|---|---|
| `sid` | **无条件** | relay 下发的 `device_sid`（见 §2.2） | 中继会话 id，也是 `auth_*` 帧的 `device_sid` | ✅ |
| `hash` | **无条件** | `createPassHash(createPassword())`（§3.1） | **配对密钥材料 = HMAC 的 key** | ✅ |
| `t` | **无条件** | `Date.now()`（**毫秒**，十进制字符串） | 生成时间戳 | ✅（解析侧必填） |
| `mid` | `deviceMid?.trim()` 非空 | `main-index.js` 的 `deviceMid`（`nt=Cn()`） | 设备指纹；**同时用于 relay WS 的 `?mid=` 与 `X-Device-ID` 头** | ⭕ |
| `name` | `deviceName?.trim()` 非空 | `e.deviceName`（`aK()`） | 桌面端显示名；移动端只拿它当**显示名兜底** | ⭕ |
| `app_version` | `appVersion?.trim()` 非空 | `bm = Y || app.getVersion()` = `3.15.3` | **桌面端版本号**，承重（§1.5） | ⭕ |
| `theme` | **永不写入** | 形参 `l`，**函数体未引用** | — | ❌ |

> **`theme` 的真相**：`ace` 的形参表里有 `theme:l`，但函数体 6 个 `searchParams.set` 里没有它。
> 调用方 `TT(h, C, A)` 也确实把 `C.theme` 传进来了（`main-index.js` @409712 的 `TT(ir,q,C.theme)`），
> 传进去被**静默丢弃**。所以桌面端二维码 URL **永远不含 `theme`**。
>
> 而移动端解析器**是认 `theme` 的**（§1.4），且只接受 5 个白名单值。结论：
> **`theme` 是一个只有手改/复制粘贴 URL 才能用上的参数**，桌面端自己从不生成。

### 1.4 与移动端解析器的逐字对照（权威反向校验）

`Bd` 在 `src-AL-_ONNp.js` 里导出为 `D`。它收一个 **`URLSearchParams` 型对象**
（`V` 用 `.get()` 取值 —— `URLSearchParams.get` 会解码 `%XX` **且把 `+` 解成空格**；
⚠️ 调用点的实参构造未逐字追到，按 `.get`/`.trim` 的用法判定为 `URLSearchParams`，**标记为推断**）。

**原文（`Reference_web/3.15.3/assets/src-AL-_ONNp.js` @62960）：**

```js
function V(e,t){return e.get(t)?.trim()||void 0}                                  // @62562
function Ld(e){return e===`light`||e===`dark`||e===`zai-light`||e===`zai-dark`||e===`system`}  // @62610

function Bd(e){
  let t=V(e,`sid`),n=V(e,`hash`),r=V(e,`t`),i=r?Number(r):NaN,a=V(e,`theme`);
  return !t||!n||!Number.isFinite(i)?null:{
    deviceSid:t, passHash:n, timestamp:i,
    ...V(e,`mid`)?{deviceMid:V(e,`mid`)}:{},
    ...V(e,`name`)?{deviceName:V(e,`name`)}:{},
    ...V(e,`app_version`)?{appVersion:V(e,`app_version`)}:{},
    ...Ld(a)?{theme:a}:{}
  }
}
```

**生成侧 × 解析侧 一致性核对：**

| 项 | 桌面端生成 | 移动端解析 | 结论 |
|---|---|---|---|
| 必需集 | 恒写 `sid`/`hash`/`t` | `!t\|\|!n\|\|!Number.isFinite(i)` → `null` | **完全一致**，必需集就是 `{sid,hash,t}` |
| `t` 类型 | `String(Date.now())` → 毫秒十进制 | `Number(r)` 后 `Number.isFinite` | 一致（不校验量级，只校验可转数字） |
| `mid`/`name`/`app_version` | 非空才写 | `V()` trim 后空 → 丢弃 | 一致（空串两边都当"没有"） |
| `theme` | **从不写** | 白名单 `{light,dark,zai-light,zai-dark,system}` 才收 | **单向不对称**：生成侧不产出、解析侧能收 |
| 大小写 | `URLSearchParams` 原样 | `URLSearchParams.get` 原样 | 一致 |
| 编码 | `URLSearchParams.set` → `+` 编成 `%2B`、`/` 编成 `%2F`、`=` 编成 `%3D` | `URLSearchParams.get` 自动解回 | 一致 |

> ⚠️ **编码陷阱（重要）**：`hash` 是**标准 base64**，天然含 `+` `/` `=`。桌面端用
> `URLSearchParams.set` 序列化，这三个字符分别变成 `%2B` `%2F` `%3D`，所以**线上 URL 里
> 不会出现裸 `+`**。但任何把 query 按 `application/x-www-form-urlencoded` 解析（`+` → 空格）
> 的实现，只要遇到**手抄/截断**过的 URL（`+` 被还原成裸字符），就会把 `hash` 解错
> ⇒ HMAC key 错 ⇒ `AUTH_FAILED`。我们的 `connection_params.rs` 正是 `+` → 空格
> （`decode_query_component`，`rust/crates/protocol/src/connection_params.rs:344-347`），
> 与桌面端**在正常 URL 上等价**，但对被改过的 URL 会静默算出错 proof。

⇒ **`app_version` 是承重的**，但承重方式是「**桌面端自己**用它挑路径」：

## 2. 配对流程时序

### 2.1 两端状态机

桌面端 relay 客户端的状态集合（`setState` 的日志白名单，`main-index.js` @388035 附近）：

```js
setState(t){…this.options.onStateChange(t),
  (t==="connecting"||t==="registering"||t==="authenticating"||t==="waiting_terminal"||t==="paired"||t==="kicked")&&this.options.logger.info("[web-remote-control] external relay device state",{state:t})}
```

另有 `"idle"`（@379963）与 `"error"`（@387621/@387773）。**桌面端没有 `"waiting"`，它叫 `waiting_terminal`**。

外层 `status` 映射（`mapTransportState`，`main-index.js` @405774）：

| relay state | 外层 `status` | 副作用 |
|---|---|---|
| `connecting` / `registering` / `authenticating` | `mobileConnected ? "active" : "starting"` | — |
| `waiting_terminal` | `mobileConnected ? "active" : "running"` | `mobileConnected=false` |
| `paired` | `"active"` | `hasEverPaired=true`、`mobileConnected=true`、打点 `pairKind: hasEverPaired?"reconnect":"initial"` |
| `kicked` | （不改 status） | `session-conflict` 失败 + 发 `external-relay-kicked` |
| `error` | `"error"` | 打点 `errorCategory:"relay"` |

移动端状态集合（`index-BGa3KiRe.js` @6405804 附近）：`idle / connecting / authenticating / waiting / paired / reconnecting / suspended / kicked / error`。

```
14 状态 → paired；onSendReady → replayUnacknowledged()  状态 → paired；waitForPaired 放行

```

**重连（`hasEverPaired=true`）**：跳过 2–3，直接 `auth_init{role:"device"}`；`pair_status:"matched"` 到达时
`lastPairedSocketGeneration` 与 `socketGeneration` 比较，产出 `{kind:"same-socket"|"reconnected-socket"}` 传给 `onSendReady`。

### 2.4 `pair_status` 的取值与迁移

**原文（桌面端 `applyPairStatus`，`main-index.js` @383203）：**

| `pair_status` | 桌面端（未配对过） | 桌面端（`wasPaired`） | 移动端 |
|---|---|---|---|
| `"waiting"` | `→ waiting_terminal`，起心跳 | `staleWaitingCount++`；第 1 次挂 15 s 恢复定时器，第 2 次立即重连 | `→ waiting`，起 `waitingTimer`（30 s 到点报 `invalid-mobile-connection`） |

> 其余静默。`"unmatched"` / `"none"` / `"pending"` 之类的猜测**在本代不存在**。

### 2.5 `pair_status_query` 的作用与心跳参数

- **作用**：**轮询配对状态**。两端都用它当心跳（keepalive + 状态确认 + ack 看门狗喂狗）。
  桌面端只在 `state === "paired" || state === "waiting_terminal"` 时发（`main-index.js` @385306）；
  移动端只在 `state === "paired" || state === "waiting"` 时发（`index-BGa3KiRe.js` @6413517）。
- **回包**：中继回 `pair_status_ack{pair_status}`（两端都把它与 `auth_ack` 同一分支处理）。
- **间隔**：`pce(interval, jitter, random)` → **`[interval-jitter, interval+jitter]` 的均匀分布**，
  默认 `interval=10000`、`jitter=oL(10000)=min(2000, floor(10000*0.2))=2000`
  ⇒ **10 s ± 2 s（8–12 s）**。原文 `chunk-OW6EUS2G.js` @781476 / @781704：


- **ack 看门狗**：`heartbeatAckTimeoutMs ?? 3e4` = **30 s**，超时 → 记 warning
  `"external relay heartbeat ack timeout, reconnecting"` 并 `reconnectAfterStaleWaiting(jitter)`
  （`main-index.js` @386037；移动端同构，`index-BGa3KiRe.js` @6413327）。
- **重连退避**：`mce(reconnectJitterMs ?? min(heartbeatJitter, 2000))` = `[0, 2000]` 均匀
  （`chunk-OW6EUS2G.js` @781902）。
- **stale-waiting 恢复**：桌面端 `scheduleStaleWaitingRecovery` 用 **15 000 ms**（`main-index.js` @386802）；
  **移动端用 1 500 ms**（`index-BGa3KiRe.js` @6414466 `staleWaitingRecoveryMs??1500`）。**两端不同。**

### 2.6 成功判据

**唯一判据：收到 `pair_status === "matched"`（经 `pair_status_ack` 或 `auth_ack` 任一携带）。**

- 桌面端：`applyPairStatus("matched")` → `state = "paired"` → `onSendReady` → `replayUnacknowledged()`
  （重放未确认的出站业务帧）；外层 `status = "active"`。
- 移动端：同一条件 → `state = "paired"` → `resolvePairedWaiters()`（`waitForPaired` 默认 15 s 超时，
  失败抛 `"Web remote control relay did not recover before timeout."`）→ 发 `bootstrap-request`。
- **「QR 就绪」不等于「配对成功」**：桌面端 `Uc` 闸门在 `waiting_terminal` **或** `paired` 任一到达时就放行
  （`onStateChange: (Pe==="waiting_terminal"||Pe==="paired")&&He&&xT()`，`main-index.js` @408166），
  即**二维码在还没有任何手机连接时就已经显示出来了**。

## 3. 证明校验

### 3.1 口令从哪来（三步生成，`main-index.js` @412161）

**原文：**


| 步骤 | 表达式 | 输出形态 | 长度 |
|---|---|---|---|
| ① 生成口令 | `randomBytes(24).toString("base64url")` | base64url 无 padding（`A-Za-z0-9-_`） | 32 字符 |
| ② 口令 → passHash | `createHash("sha256").update(password).digest("base64")` | **标准 base64**（`+` `/` `=` 都可能出现） | 44 字符（含 1 个 `=`） |
| ③ passHash 进 URL | `URLSearchParams.set("hash", passHash)` | `+`→`%2B`、`/`→`%2F`、`=`→`%3D` | — |

调用点（`main-index.js` @407522）：

```js

    Se=re?{mode:"persisted",deviceSid:re.deviceSid,passHash:re.passHash}
         :{mode:"register",passHash:e.authProvider.createPassHash(e.authProvider.createPassword())}
```

⇒ **只有「首次配对（没有已存凭据）」才现场造口令**；已存凭据（`mode:"persisted"`）直接复用旧 `passHash`
⇒ **重启应用后二维码不变**（同一个 `sid` + 同一个 `hash`），手机可以继续用旧链接。

### 3.2 proof 输入串的逐字复核

**桌面端（Node crypto，`main-index.js` @412328）：**

```js
calculateProof: s((e,t,r,n)=>h0("sha256",e).update(`${t}|${r}|${n}`).digest("base64url"),"calculateProof")
//                     ↑passHash ↑nonce ↑role ↑deviceSid
```

**移动端（WebCrypto，`index-BGa3KiRe.js` @6404393）：**

```js
async function L3n(e,t,n,r){
  let i=new TextEncoder,
      a=await globalThis.crypto.subtle.importKey(`raw`,i.encode(e),{name:`HMAC`,hash:`SHA-256`},!1,[`sign`]),

```

**移动端 base64url 编码器（`index-BGa3KiRe.js` @6404282）：**

```js
function I3n(e){return btoa(String.fromCharCode(...e)).replace(/\+/g,`-`).replace(/\//g,`_`).replace(/=+$/,``)}
```

**三方逐字一致：**

| 项 | 桌面端 | 移动端 | 我们的 `proof.rs` |
|---|---|---|---|
| 密钥 | `h0("sha256", e)`，`e = passHash` 字符串（Node 默认 UTF-8） | `importKey("raw", TextEncoder.encode(passHash))` | `HmacSha256::new_from_slice(pass_hash.as_bytes())` ✅ |
| 消息 | `` `${t}|${r}|${n}` `` = `nonce\|role\|deviceSid` | 同 | `nonce` + `b"\|"` + `role` + `b"\|"` + `device_sid` ✅ |
| 转义 | 无（裸拼接） | 无 | 无 ✅ |
| 编码 | `.digest("base64url")` | `btoa` → `+`→`-`、`/`→`_`、去 `=` | `URL_SAFE_NO_PAD` ✅ |
| 输出 | 43 字符 | 43 字符 | 43 字符 ✅ |

> **权威结论：`proof = base64url_nopad(HMAC-SHA256(key = passHash 的 UTF-8 字节, msg = "nonce|role|deviceSid"))`。
> `role` 不是常量 —— 它由「本端扮演的角色」决定，见 §3.3。**

### 3.3 角色：`device` vs `terminal`（关键差异点）

| 端 | `auth_init.role` | `calculateProof` 的 role 实参 | 原文坐标 |

| **移动端（控制方）** | `"terminal"` | `"terminal"` | `index-BGa3KiRe.js` @6407515（auth_init）、@6410620（auth_response） |

**原文（桌面端 `auth_response`，`main-index.js` @382657）：**

### 3.4 校验在哪一步、失败怎么表现

**校验位置：不在桌面端，也不在移动端 —— 在中继服务端**（两端都只是「算 proof 发出去」，本地不做任何比对；
代码里搜不到任何 `proof` 的比较逻辑）。

**失败表现（`error.code` 分支）**

桌面端 `handleRelayError`（`main-index.js` @383911）：


|---|---|---|

## 5. 解绑 / 失效

### 5.1 三条路径

| 操作 | 入口 | 桌面端动作 | 凭据后果 |
|---|---|---|---|

| **中继判 AUTH_FAILED** | 自动 | `onInvalidPersistedAuth` → `yS(…,"auth-failed")` | `deviceSid` 清掉；**`passHash` 保留**，同口令重新注册 |

```js

  error:"Desktop disconnected this Web remote control session."}),t.delete(h),d.delete(h),w(A),_(A),x(A),
  A.pendingOutboundPayloads.length=0,A.transport.dispose(),e.disposeWorkspaceHostAttachmentsForWindow(h,C),…)}
```

⇒ 停止 / 重置 / 关窗时，桌面端在断链前**尽力发一帧业务帧**
`{zcode_type:"app-error", reason:"desktop-disconnected", error:"Desktop disconnected this Web remote control session."}`。
移动端把它映射成 `desktop-disconnected`（4010）⇒ *"Desktop Offline — The desktop side disconnected."*。

另有一条终态失败路径 `ht`（`preserveWindowRuntimeFailure`，`main-index.js` @396400 附近），
同样先发 `app-error` 再把 `status="error"` 固化：

```js
function ht(h,C,A,N){C.status==="error"&&C.failure?.reason===N.reason||(le(C,{zcode_type:"app-error",reason:N.reason,error:N.message??N.reason}),…,C.status="error",C.error=N.message,C.failure=N,t.set(h,C),…)}
```

**旧链接失效后的移动端表现（两条互斥可能，取决于中继实现）：**

| 中继返回 | 移动端文案 |
|---|---|
| `session-not-found`（4004） | *"Access Link Expired — This Web remote control link no longer exists, usually because desktop generated a new QR code."* |
| `AUTH_FAILED` / `WRONG_PARAM` | *"Mobile Connection Invalid — The QR parameters or authentication proof for this page are no longer valid. Do not reuse an old screenshot or copied link."* |

⚠️ **未能证实**：`resetPairing` 之后中继**是否换 `device_sid`**。文案把「桌面端重新生成二维码」
归因给 `session-not-found`，暗示 `sid` 也换了；但 `device_register_init` 只带 `device_mid`（未变），
中继完全可以让同一 `mid` 复用旧 `sid`（那样旧链接会命中 `AUTH_FAILED` 而非 `session-not-found`）。
**需要在真实中继上抓一次「重置前后同一旧链接的 `error.code`」才能定论。**

## 6. 多设备

**语义：抢占（takeover），不是并存、也没有上限计数。**

证据链：

1. 桌面端只存**一份**凭据（§4.2）⇒ 所有扫码的手机拿到的是**同一个 `sid` + 同一个 `passHash`**，
   也就是说**任意台手机都能通过认证**，配对层不做排他。
2. 排他在**中继**侧，通过 `error.code = "KICKED"` 体现：
   - 桌面端 `if(t==="KICKED"){…logger.warn("[web-remote-control] external relay device KICKED, reconnecting"),this.socket?.close();return}`
     （`main-index.js` @383939）—— 桌面端被踢后**自动重连**，抢回来。
   - 移动端 `if(e==='KICKED'){this.setState('kicked'),this.enterTerminalFailure(z9('session-conflict',t||e));return}`
     （`index-BGa3KiRe.js` @6411936）—— 手机被踢后**终态失败**，不再自动重连。
3. 移动端文案把这个语义写死了（`index-BGa3KiRe.js` @6424518）：

> *"Taken Over By Another Device — Another remote control device connected and replaced this phone.
> **Only one mobile controller can stay active at a time.**"*

**推论（⚠️ 推测部分）**：后到的手机连上后中继踢掉先到的；先到的手机看到 `session-conflict` 必须
重新扫码（文案下一步就是 *"Scan the desktop QR code again to use this phone."*），
而桌面端因为自动重连会重新占位——即**最终稳态是「最后连接的那台手机在线」**。

**没有「设备上限」常量**：全包检索不到 `maxDevices` / 设备数上限之类的东西。
"只有一台"是中继的会话模型约束，不是桌面端代码里的数字。

## 7. 与我们的实现的差异

对照：`rust/crates/protocol/src/`（`proof.rs`、`connection_params.rs`、`relay_client.rs`、`device_info.rs`）、
`android/app/src/main/kotlin/app/zemote/pairing/PairingUrl.kt`、`data/{DeviceRecord,DeviceStore,SecretCipher}.kt`。
（**只读，未改动。**）

### 7.1 一致项（已逐字复核，**不需要改**）

| 项 | 桌面端 | 我们 | 判定 |
|---|---|---|---|
| proof 算法 | `hmac-sha256(passHash).update(\`${nonce}\|${role}\|${deviceSid}\`).digest("base64url")` | `proof.rs:57-82` | ✅ 逐字一致 |
| proof 的 role | 移动端 `"terminal"`（桌面端是 `"device"`） | `relay_client.rs:553` `"role": "terminal"` | ✅ 一致（我们扮演的是终端；**不要**改成 `device`） |
| proof 输出 | 43 字符 base64url 无 padding | `URL_SAFE_NO_PAD` | ✅ |
| 必需参数集 | `{sid,hash,t}` | `connection_params.rs:454-459` | ✅ |
| `t` 解析 | `Number(r)` + `Number.isFinite` | `parse_int_like_dart` | ✅（都只要求可转数字） |
| 可选参数 | `mid`/`name`/`app_version`/`theme` | `connection_params.rs:464-467` | ✅ 四个都在 |
| `theme` 白名单 | `{light,dark,zai-light,zai-dark,system}` | **未做白名单**（`String` 直通） | ⚠️ 宽松，见 7.2-⑤ |
| `auth_init.meta` 形状 | `{platform,version,name}` | `device_info.rs` | ✅ |
| `meta.version` 回落 | 移动端 `appVersion ?? "web"` | `relay_client.rs:349-352` 同 | ✅ |
| 心跳间隔 | `[8s,12s]`（10s±2s） | `HEARTBEAT_INTERVAL_MS = 10_000` | ✅ 数值一致 |
| ack 看门狗 | `3e4` = 30 s | `HEARTBEAT_ACK_TIMEOUT_MS = 30_000` | ✅ |
| `pair_status` 取值 | 仅 `waiting`/`matched` | `relay_client.rs:680+` 同 | ✅ |
| `pair_status_query` 形状 | `{type,device_sid,client_ts}` | `relay_client.rs:911` | ✅ |
| waiting 超时 | 移动端 `waitingTimeoutMs ?? 3e4` | `WAITING_TIMEOUT_MS = 30_000` | ✅ |
| relay WS 带 `?mid=` | 两端都有 | `connection_params.rs:487-490` | ✅ |

### 7.2 不一致项（逐条，带坐标）

**① `meta.name` 取值不同（低危，可能影响桌面端显示名）**

| | 值 |
|---|---|
| 网页移动端（权威客户端） | `"mobile-browser"`（`index-BGa3KiRe.js` @6407515） |
| 我们 | `"zemote"`（`rust/crates/protocol/src/device_info.rs:20` `ZEMOTE_APP_NAME`，用于 `relay_client.rs:353`） |

`device_info.rs:3-4` 的注释明确说这是**有意的**（"网页端把自己谎报为浏览器；Zemote 如实上报自己"），
但**桌面端从未校验过 `meta`**（控制帧无 schema），所以这是产品选择而非协议错误。
**桌面端是否用 `meta.name` 展示"已连接客户端"名字——未能证实**（`meta` 在 `main-index.js` 里只被原样转发）。

**② `meta.platform` 取值不同（同上，有意）**

| | 值 |
|---|---|
| 网页移动端 | `"web"` 常量 |
| 我们 | 真实平台（`android`/`ios`/…；`device_info.rs:52-56`） |

**③ relay WS 地址的推导方式不同（中危）**

| | 规则 |
|---|---|
| 网页移动端 | **硬编码** `wss://zcode.z.ai/ws`：`B6n()` = `Se({endpointOrigin:"https://zcode.z.ai",overrideUrl:void 0})`（`index-BGa3KiRe.js` @6454717），`Se` ≡ `validation-CqXZOLXO.js` 的 `Rv`（@213995），`Rv` 返回 `overrideUrl \|\| (origin==='https://zcode.chatglm.site' ? 'wss://zcode.chatglm.site/ws' : Dv)`，`Dv='wss://zcode.z.ai/ws'`（@212356） |
| 我们 | 从配对 URL 的 host 推导：`connection_params.rs:474-491` `relay_ws_uri()` → `wss://<source.host>[:port]/ws` |
| Dart 参考实现 | 同我们（`Reference_code/lib/protocol/connection_params.dart:61-71`） |

⇒ 生产 URL（host = `zcode.z.ai`）下**行为等价**。差异只在「桌面端配了自定义
`zcodeEndpointOrigin` / `ZCODE_WEB_REMOTE_CONTROL_URL`」时显现：那时网页端仍会连 zcode.z.ai（它自己的 bug），
而我们连 URL 里的 host（更正确）。**建议保留我们的行为**，但要知道这是**我们与网页端的既存分歧**，
不能拿网页端行为当"应该硬编码"的论据。

**④ `staleWaitingRecoveryMs` 不同（低危）**

| | 值 |
|---|---|
| 桌面端 | **15 000 ms**（`main-index.js` @386802 `scheduleStaleWaitingRecovery`） |
| 网页移动端 | **1 500 ms**（`index-BGa3KiRe.js` @6414466 `staleWaitingRecoveryMs??1500`） |
| 我们 | 未见对应常量（`relay_client.rs` 只有 `RECONNECT_WAIT_TIMEOUT_MS = 20_000` / `DEAD_LINK_THRESHOLD_MS = 25_000`） |

⚠️ 我们这两个常量（20 s / 25 s）**在桌面端与网页端都找不到对应值**——需确认是 Dart 参考实现自创，
还是从别的路径移植。**未证实其权威性。**

**⑤ `theme` 未做白名单（低危）**

网页端只接受 `{light,dark,zai-light,zai-dark,system}`（`src-AL-_ONNp.js:62610` 的 `Ld`）；
`connection_params.rs:467` 把 `theme` 原样收进 `Option<String>`，`connection_params.rs:642-648` 的
`parse_theme` 测试也只测 `"dark"`。**我们更宽松**（不会误拒，但把非法值传下去了）。
另注意 `connection_params.rs:4` 的文档串把 URL 写成含 `&theme=...`，
而**桌面端生成器从不写 `theme`**（§1.3）——文档串与现实不符，建议修正。

**⑥ `nonce` 缺失的兜底不同（低危）**

| | 行为 |
|---|---|
| 我们 | `relay_client.rs:619-631` 对缺失 `nonce` 回退成 `''` ⇒ 拼出 `"|terminal|SID"` |
| 桌面端 / 网页端 | `t.nonce` 为 `undefined` 时模板串拼出**字面量** `"undefined|device|SID"` / `"undefined|terminal|SID"` |

这是 `proof.rs:39-42` 的 PORT-NOTE 明确记录过的移植选择（照抄 Dart 的 `?? ''`）。
**实测影响极小**（中继一定带 `nonce`），但既然对端行为已被复核出与 Dart 不同，
这条差异应写进已知偏差清单，别当成"已对齐"。

### 7.3 未实现项

**① 没有 `device_register_init` / `device_register_ack` 路径（**有意**，我们永远是 terminal）**

我们只扮演移动端，永远走 `auth_init{role:"terminal"}`，不需要注册帧。
但**桌面端会在首连时发 `device_register_init`**——如果我们将来要做"被控端"角色，
这条路径是必需的：`{type,device_mid,pass_hash,meta,client_ts}` → `{type:"device_register_ack",device_sid}`
（`main-index.js` @380835 / @382199）。**当前未实现。**

**② `device_sid` 的来源假设不同**

桌面端的 `sid` **由中继下发**（`device_register_ack.device_sid`），桌面端自己**不生成** sid。
我们的 `DeviceStore` 把 `sid` 当"URL 里的既有值"（`DeviceStore.kt:147` 用 `host+sid` 去重），
这本身没错（我们只消费），但**如果**将来要复刻桌面端，必须知道 `sid` 不是本地生成的。

**③ `error.code` 只处理了 `KICKED`，其余四个全部静默（中危，已确证）**

`relay_client.rs:720-757` 的 `handle_relay_error` 全部逻辑就是：

```rust
out.push(RelayEvent::Log(format!("[relay] error frame: {} {}", …)));   // ← 先无条件记一行
if code == Some("KICKED") { … }                                        // ← 唯一的分支
// 函数到此结束：AUTH_FAILED / WRONG_PARAM / DEVICE_OFFLINE / INTERNAL 只留下一行日志
```

对照表（对端行为取自 §3.4）：

| 码 | 桌面端 | 网页移动端 | 我们（`relay_client.rs:720-757`） |
|---|---|---|---|
| `KICKED` | 处理（关 socket 重连） | 处理 → `session-conflict` 终态 | ✅ 处理（含 `kick_recovery_attempted` 一次性重连） |
| `AUTH_FAILED` | 处理（清凭据+重注册） | 处理 → `invalid-mobile-connection` | ❌ **无分支**（仅日志） |
| `WRONG_PARAM` | 处理 | 处理 → `invalid-mobile-connection` | ❌ **无分支** |
| `DEVICE_OFFLINE` | **不识别**（落 `enterError`） | 处理（`recoverFromDeviceOffline`） | ❌ **无分支** |
| `INTERNAL` | 处理（退回 waiting / recoverable） | 处理 | ❌ **无分支** |

后果：中继把移动端判为「链接/证明失效」（`AUTH_FAILED`/`WRONG_PARAM`）时，
我们**不会进入失败态、不会提示用户重新扫码、也不会停止心跳**——只能等 ack 看门狗
30 s 超时后重连，然后被中继再拒一次，形成「连上→无反应→超时→重连」的静默循环。
**建议按上表补齐 `AUTH_FAILED` / `WRONG_PARAM` / `DEVICE_OFFLINE` / `INTERNAL` 四个分支**
（语义照 §3.4 的表）。

> 附带说明：我们另有一套 **WebSocket 关闭码 → 原因串** 的映射
> （`relay_client.rs:125-136` `relay_close_reason`：4004/4009/4010/4011/4012/4013 →
> `session-not-found`/`session-conflict`/`desktop-disconnected`/`session-expired`/`workspace-closed`/`invalid-mobile-connection`），
> 与 `error.code` 是**两条独立机制**，不要互相替代。网页端同一份数值枚举在
> `src-AL-_ONNp.js` @63288（`var H={SessionNotFound:4004,…InvalidMobileConnection:4013}`，
> 导出为 `O`），映射函数 `Vd` @63433。

**④ `app-error` 业务帧（`reason:"desktop-disconnected"`）完全未处理（中危，已确证）**

桌面端停止 / 重置配对 / 关窗时**主动推**一帧业务帧
`{zcode_type:"app-error",reason:"desktop-disconnected",error:"Desktop disconnected this Web remote control session."}`
（`main-index.js` @396850 的 `ne()`；另有 `ht()` @396400 发任意 `reason`）。

`grep -rn "app-error|app_error" rust/ android/` **零命中**：我们的 Rust 与 Android 都没有这条路径。
`relay_client.rs:611-670` 的分发只认 `auth_challenge` / `auth_ack` / `pair_status_ack` / `data` / `error`，
`data.payload` 之后的 `zcode_type` 分发（`conversation_transport.rs`）也不含 `app-error`。
⇒ 我们只能靠 **socket close + 关闭码 4010**（`relay_client.rs:791`）去推断"桌面端主动下线"，
而**桌面端在主动下线时并不保证带 4010 关闭码**（它只是 `transport.dispose()`）。
**建议补 `app-error` 的接收处理**，把它映射成与 `desktop-disconnected` 同一个用户可见原因。

**⑤ 桌面端凭据存储格式与我们的不同（不构成不兼容，仅记录）**

| | 格式 |
|---|---|
| 桌面端 | `enc:v1:<b64url(iv)>.<b64url(tag)>.<b64url(ct)>`，三段点分；密钥 `sha256(ZCODE_CREDENTIAL_SECRET \|\| fallback)` |
| 我们 | `enc:v1:<b64url(iv \|\| ct)>`，单段拼接；密钥在 Android Keystore（`SecretCipher.kt:57,71`） |

两者**前缀相同、布局不同**。因为两个 app 的存储互不读取，**不构成互操作问题**；
但如果将来要做「导出/迁移」，这个前缀相同会被误认成兼容格式，**必须显式区分**。

**⑥ 配对 URL 的生成能力完全缺失（低危，视需求）**

`PairingUrl.kt` 只做**前置筛查**（`preflight`）与 `name`/`host+sid` 提取，
没有 `buildWebRemoteControlExternalQrUrl` 的对应实现。我们不做被控端时不需要，
但要清楚：**我们的 `PairingUrl.kt` 与 `connection_params.rs` 都是"消费方"，不是"生成方"。**
若要做生成，权威形态见 §1.2，且注意 **`theme` 不写**、**`t` 用毫秒**、**`mid`/`name`/`app_version` 非空才写**。
