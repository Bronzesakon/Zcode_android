## A. 本域功能概览（给非工程师看）

**这是这个壳存在的理由。** 你的任务在桌面端跑着，人却拿着手机走开了；这一域的功能就是让手机替你盯着：

- **任务在跑** → 手机通知栏常驻一条「运行中 · 任务名」，正文是 AI 最新一段话。
- **任务要你确认**（要授权、要你回一句话）→ 补发一条**会响**的提醒；同一处交互只响一次，不会反复吵你。
- **任务结束**（跑完 / 你中断 / 失败）→ 那条**同一条**卡片原地把状态词换成「已完成 / 已中断 / 已失败」，正文冻结在最后一句，并挂一个「知道了」按钮。
- **在支持的机型上**（Android 16 / ColorOS 16），同一条记录会被系统提升成**实时更新卡片**，ColorOS 上渲染成**流体云**（状态栏芯片 + 可展开的圆角卡片）——不用解锁、不用开 App 就能看到"AI 现在写到哪了"。

数据流向（简化）：

```
桌面端 ──sessions-index（哪些任务、什么状态、什么标题）
       ──会话流 turnHeader / 对话正文 ──┐
                                        ▼
                        壳：TaskStore（合并三路运行态 + 决定"谁算在跑"）
                                        ▼
                       NotifyState（相位转移 ⇒ 完成 / 待确认事件）
                                        ▼
                  Notifier（发通知）── PromotionPolicy（抢提升位）── 系统 ⇒ 流体云卡片
```

用户**感知不到**、但决定体验的两件事：卡片**多久刷新一次正文**（后台时段、单工作区约每 12–20 秒一次；同时跑 N 个工作区时约 N × 12 秒），以及卡片**是不是同一条记录**（原地改状态而不是撤掉重建）。前者是 C7 所在的位置；后者由判定层（B1 所在的 `NotifyState`）和渲染层共同保证。B4 则属于"待确认要响、且只响一次"这条支线。

## B. 本域架构小结

分四块，边界很清楚：

1. **判定层（本体）**：`core/NotifyState.kt` —— 纯逻辑、无 Android 依赖，能在电脑上跑单测。它决定"什么算在跑"（`running`/`prewarming`）、"什么算结束"（终态，且必须**持续停 3 秒**才算，见 `COMPLETION_HOLD_MS`）、"待确认只响一次"。
2. **账本层（本体）**：`core/TaskStore.kt` —— 把三条来源的运行态合成一份，并**自己重新算一遍**要发通知的运行清单（`buildRunningList()`，现 `TaskStore.kt:844-869`；运行中＝相位 ∈ `RUNNING_PHASES` **或**在观察窗里，`runningIn()` `:214-216`）。`NotifyState` 只回灌"观察窗"的时刻与归属（B1 执行后它不再产出运行清单）。
3. **渲染层（本体）**：`notify/Notifier.kt` + `notify/LiveUpdate.kt` —— 真正发通知、挂动作、请求系统提升成流体云。
4. **抢位与节奏（脚手架）**：`core/PromotionPolicy.kt`（谁抢得到提升位）、`core/PreviewSettle.kt`（正文"安静 250ms 再推"）、以及 `ShellRuntime` 里那个**每 12 秒重挂一次订阅**的轮询器（C7 所在）。

**要保住这个功能，必须留的是 1–3。** 第 4 块是可以调、可以换实现的部分；C7 只动第 4 块里的一台"节拍器"。

### C7. 任务通知与实时更新卡片 —— 后台时段"每 12 秒重挂一次订阅"的节拍器（`LIVE_REANCHOR_EVERY_POLLS` 与 `livePolls` 取模）  [`C/建议只标注`]

> ✅ 已于 2026-09-18 落地（b627610，按本节建议"保留并说明理由"执行，**值仍冻结为 1**）：`ShellRuntime.kt:612-637` 的 KDoc 现在完整写着本节的全部结论——"本值是唯一把两种节奏分开的旋钮（2026-09-18 复核）"、两条跨文件约束（门槛 < 拍长、12s 重挂预算）、以及"⚠️ 绝不要改这个值"。原"删了会怎样"里那条**只有真机才看得见的隐患**（`livePolls` 自增在 in-flight 守卫之前）也已就地写成注释（`ShellRuntime.kt:665-668`：「本批只记录、不修」）。机制本身（2026-09-19 核实仍然成立）：拍长 `LIVE_PROGRESS_POLL_MS = 12_000L`（`:610`）、声明 `:638`、计数 `:644`、自增 `:669`、取模 `:671`、轮询器 `:656-691`。以下原始分析保留存档，行号为清理前旧值。
- **功能归属**：任务通知与实时更新卡片（卡片正文的刷新节奏），跨到**多工作区承载与轮换**与**原生承载（Native Carrier）**：这条代码决定的是"卡片正文多久动一次"。
- **这个功能是干什么的**：**先讲清这 12 秒是干嘛的。** 你退到后台后，网页被系统冻结，壳（原生承载）自己开一条 relay 连接顶上，卡片才不会停更。但桌面端**同一时刻只服务一座桥**，而且**只在被"重订阅/resync"时才推一份新快照**——不重挂，卡片正文就会停在上一轮开头几十分钟不动（`ShellRuntime.kt:274-286` 的现场记录）。所以壳后台时段跑一个轮询器：每 12 秒做一次"重挂"（`NativeRelayClient.reanchorProgress()` → 轮到最饿的那座桥、只重订阅该桥最饿的一条会话），逼桌面端再推一份快照，把最新一行正文喂上卡片。**用户感知**：流体云卡片上的那行正文有没有在跟着动——现行节奏下单卡约 **12–20 秒**换一次；如果这个节拍被调慢，用户看到的就是"卡片半分钟不动"。
- **这条代码的角色**：它是节拍器上的一个旋钮 + 一个计数器。`LIVE_PROGRESS_POLL_MS = 12_000L` 是**拍长**（每 12 秒跑一次轮询），`LIVE_REANCHOR_EVERY_POLLS` 是"每几拍重挂一次"，`livePolls` 是已经跑了多少拍的计数，`livePolls % LIVE_REANCHOR_EVERY_POLLS == 0` 决定这一拍要不要重挂（`ShellRuntime.kt:327-336`）。**现行值是 1**，所以这个取模**恒为真**、计数器取值**永远不影响任何结果**，`if (reanchor)` 那一支**恒被进入**。它不是功能的开关，是同一个功能的"可调档位"。
  这个旋钮有真实历史（清理前 `ShellRuntime.kt:289-300` 的注释、README 要点 20；现行注释在 `ShellRuntime.kt:612-637`、公式在 README:522-525）：`2`（24s 轮换）真机 151 验收过"0 失败、卡片零抽动"，单卡间隔约 24–40s；`4`（48s）实测"卡片肉眼可见地半分钟不动"**已被否决**；`1` 是 2026-09-17 用户拍板调快的现行值，代价是回收/重订频率翻倍。它还被**跨文件引用**：`core/RelayBridge.kt` 的门槛 KDoc（现 `:737-743`）把"门槛必须小于拍长"写成 `LIVE_PROGRESS_POLL_MS × LIVE_REANCHOR_EVERY_POLLS`，README 要点 20 也写明这条公式与"门槛 `ROTATE_MIN_STARVE_MS`（8s）必须小于拍长"的约束。
- **这个旋钮与"拍长"不是一回事（决定了它是否值得留）**：每一拍做两件事——① 对每个在跑任务重订一次对话详情（`NativeRelayClient.subscribeProgress` → 现 `NativeRelayClient.kt:225`、`RelayBridge.kt:998`，便宜、按会话）；② 可选地做一次"重挂"（`reanchorProgress` → 现 `NativeRelayClient.kt:235`、`RelayBridge.kt:1040`，贵：resync 一次 + 可能要回收换服务权，一轮 ≤6s 甚至 ~9s）。`LIVE_REANCHOR_EVERY_POLLS` 只放慢 ②，不放慢 ①。所以它**不能**用"直接把 12s 改大"来替代：改拍长会连 ① 一起放慢（新起跑的任务要多等一拍才被订上）。
  **结论：这个旋钮还挣得它的位置**——理由不是"它有历史"，而是它今天仍是**唯一**能把"贵的一轮重挂"与"便宜的每拍重订"分成两个节奏的开关；顺带它还是"一轮重挂必须在 12s 内跑完"这条预算公式里的因子（见下）。它的问题不是多余，而是**被冻结在 1 之后，取模与计数器看起来像死代码**——所以真正该做的是**标注**，不是删除。

## F. 文档遗漏补遗（2026-09-19 新增）

### F1. 通知/流体云卡片点击 → 任务详情页（d08e256，2026-09-19，本文档此前完全没有这一节）

清理收口后第二天新增的机制，解决"页面停在 KICKED 终态时点卡片进不去"：页内定位器只跑 3 秒就静默放弃，原生的 24 秒重试只等注入就绪位，而 KICKED 页面**早就就绪**——两道超时全用不上。改为**三段式**：通知带工作区键 → 预设目标任务 → 先交还承载 → 重载（页面自己实现了"重载后回到上次任务"，重载即跳转，不靠点 DOM）。关键件（行号 2026-09-19 核实）：

- **通知侧**：`Notifier.taskIntent()`（`Notifier.kt:481-504`）把 `MainActivity.EXTRA_WORKSPACE_KEY`（`MainActivity.kt:1030`，值 `"workspace_key"`）放进 intent（`:496`，2026-09-18 起）——**完成卡**（`:371`、`:400`）与**待确认卡**（`:462`）三条 PendingIntent 都走它。
- **壳侧闸门**：`MainActivity.handleIntent` 的 `ACTION_LOCATE_TASK` 分支（`:719-737`）先走 `maybeReloadForKickedPage()`（`:807-836`）：判据保守（`ShellRuntime.carrierMayHaveKickedPage()`，`ShellRuntime.kt:1087`＝承载在跑或本次后台承载跑过，**宁可不重载**）；命中则依次 `__zcodeShellPresetTask` 预设 → `ShellRuntime.handBackCarrierForLocate()`（`:1095`，先交还承载——单控制端互斥，不交还重载后会被再 KICK 一次）→ 复位就绪位（`ShellRuntime.onPageStarted()`，`:824`）→ 300ms 后 `reload()`。
- **`presetLocatePending` 让路闸门**（`MainActivity.kt:805`）：`onPageFinished` 里还有一次 `tryLocate()`，重载会触发它、抢在页面自己打开任务之前去点 DOM 而打出"页面可能已改版"假警报；有这一位，那条回调让路给 `PRESET_LOCATE_FALLBACK_MS = 9000L`（`:1040`）后的延迟兜底定位（`presetUsed = true`，`tryLocate` `:746-776` 据此调整放弃文案）。
