# 3.17.2 relay 变化核对（手机远控页）

> 2026-11-05。基线：`Reference_web/3.17.2/mobile-index.js`（设备实际加载的
> `/remote/v4/3.17.2/assets/index-BUo4VNG8.js`，6.87MB）+ `validation.js`
> （`validation-K_Srzxqn.js`，relay URL 构造 chunk）+ 3.17.1 同名文件对比。
> 结论：**relay 协议无变化**；本端（注入层 + 原生承载）有三处形状偏差，已按页面口径对齐。

## 1. 与 3.17.1 逐项对比

| 项 | 3.17.1 | 3.17.2 | 结论 |
| --- | --- | --- | --- |
| relay URL | `wss://<host>/api/v1/remote/ws2`（`Hd()` 构造） | 同字面量、同构造 | 不变 |
| token | `getToken()` 后 `?token=`，可选 `mid=` | 同 | 不变 |
| `auth_init` | `{type, device_sid, meta{platform:"web", version:appVersion, name:"mobile-browser"}, client_ts:秒}` | 同（`Mir.connect`） | 不变 |
| 心跳 | `{type:"pair_status_query", client_ts:秒}` | 同 | 不变 |
| 业务帧外层 | `{type:"data", payload, client_ts:秒}`（`prepare()`） | 同 | 不变 |
| KICKED | `kickedDelay()`；窗口内重连、超出 → `session-conflict` | 同 | 不变 |
| `maxPhysicalFrameBytes` | 有 | 有（同值路径） | 不变 |
| 握手超时 / 退避 | `Je` 超时 + `retry` 抖动 | 同结构 | 不变 |

页面侧 `Mir` 类（relay 客户端）在两版里是同一实现，仅变量名/压缩位置不同；
`relayWsUrl` 仍由 `validation` chunk 的 `Hd()` 产出。

## 2. 本端对齐（2026-11-05 修改）

`NativeRelayClient`（原生承载）旧实现与页面有三处偏差，已在 `223b519` 之后的对齐批次修正：

1. `auth_init.meta.version`：旧值恒 `"web"` → 现在用 `DesktopVersion.current()`（页面同口径：
   桌面版本号，如 `3.17.2`），学不到才退回 `"web"`。
2. 心跳 `pair_status_query`：旧实现多带 `device_sid`、`client_ts` 用**毫秒** → 现在
   `{type, client_ts:秒}`，与页面逐字一致。
3. 业务帧外层 `client_ts`：旧实现用毫秒 → 现在用秒（`dataEnvelope()` 纯函数 + 单测钉住）。

单测：`NativeRelayClientTest` +2（帧形状/版本），Kotlin 184/184。

## 3. 真机“连接中断，正在重连…”的归因（未修，属服务端/桌面端）

2026-11-05 10:51 起，手机页面（3.17.2）对 `wss://…/api/v1/remote/ws2` 的每次连接都在
0.2–1.5s 内以 **1006**（无关闭帧）结束并每 10s 重试。已排除：

- 手机网络：同一网络下 HTML/静态资源 ~100ms 加载完成；
- 版本闸门：`app_version=3.17.2`，无阻断 dialog；
- 原生承载抢连接：`carrier_off` + 整页重载后仍 1006；
- 本端协议：见 §1，3.17.1/3.17.2 relay 完全一致。

⇒ 剩余方向是服务端在 WS 升级阶段拒绝（短 token / 会话状态 / 桌面端远控开关）。
处理顺序：桌面端远控开关关开 → 手机整页重载 → 仍失败则重新扫码配对。

## 4. token 一次性与正确交接（2026-11-05 真机 CDP 实证）

两个决定性的实测（在页面内用同一 JWT 现铸 token，不打印任何凭证）：

| 实验 | 结果 |
| --- | --- |
| 同一枚 token 连续连接两次 | 第 1 次 open + `auth_ack`；第 2 次 **1006**（服务端拒绝） |
| 另铸一枚新 token 开第二条连接 | open + `auth_ack`；**页面自己的 socket 不受影响**（页面日志无新增 close） |

结论：

1. relay token 是**一次性**的。页面自己的重连复用旧 token，所以一旦断开就永远连不回去
   （“连接中断，正在重连”卡死的根因）；只有整页重载才会重新 `POST /api/v1/remote/token`。
2. 服务端**允许并存**多条控制端（不同 token）——之前“单控制端互斥”的判断只在复用同一枚
   token 时成立。
3. 正确交接：注入层只移交 **JWT**（内存、不落日志）与去掉凭证查询串的 ws URL；
   `NativeRelayClient` **每次连接/重连前**自己 `POST /api/v1/remote/token` 铸新 token，
   再拼 `?token=…&mid=…` 拨号。页面那条连接从头到尾不被碰。
4. 因此回前台不再无条件重载页面（那是“连接中断”闪屏的来源）；页面若因自身 token 失效
   卡住，由注入层的握手失败自愈兜底（连续 2 次 open 前 close → 重载一次，60s 冷却）。
