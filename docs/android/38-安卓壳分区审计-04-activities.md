## Findings

### F1. `openNotificationSettings()` — the API<26 fallback branch can never run  [UNREACHABLE]
- **Location**: `app/src/main/java/com/zcode/remote/SettingsActivity.kt:167-170` (the `else` of the guard at `:164`)
- **Symbol**: `SettingsActivity.openNotificationSettings` / `Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS).setData(Uri.fromParts("package", …))`
- **Why dead**: the branch is guarded by `Build.VERSION.SDK_INT >= Build.VERSION_CODES.O`, and `VERSION_CODES.O == 26`. `app/build.gradle.kts:36` sets `minSdk = 26`, so no device that can install the APK can ever fail that comparison. The `else` arm — the whole `ACTION_APPLICATION_DETAILS_SETTINGS` fallback — is unreachable by construction. (`Settings.ACTION_APP_NOTIFICATION_SETTINGS` and `Settings.EXTRA_APP_PACKAGE` are themselves API 26, so the guard is redundant on both sides; `README.md:683` records the "minSdk 26 because notification channels are an API 26 concept" decision.)
- **Reference search**: `VERSION_CODES\.` over `android-shell` → 5 hits (MainActivity.kt:644 `TIRAMISU`, KeepAliveService.kt:57 `UPSIDE_DOWN_CAKE`, ShellRuntime.kt:64/1835, SettingsActivity.kt:164 `O`); `minSdk|targetSdk|compileSdk` over `android-shell` → `app/build.gradle.kts:36 minSdk = 26` (confirmed by README.md:10 "minSdk 26 / targetSdk 35", README.md:683 "minSdk 26（Android 8.0）"). The two other guards are *above* minSdk (33, 34) and stay live.
- **Confidence**: high
- **Suggested action**: delete the `if/else` and keep the single `ACTION_APP_NOTIFICATION_SETTINGS` intent.
- **Risk if removed**: none functionally — the deleted arm was the "old ROM" path for a platform the app refuses to install on. `Uri` stays imported (still used at `:188`). No test covers it (`grep MainActivity|SettingsActivity` over `app/src/test` → 0 hits).

### F2. `ZcodeRemoteApp.onTerminate()` body — a callback the OS never invokes in production  [UNREACHABLE]
- **Location**: `app/src/main/java/com/zcode/remote/ZcodeRemoteApp.kt:72-76`; companion `app/src/main/java/com/zcode/remote/core/ShellLog.kt:99-101`
- **Symbol**: `ZcodeRemoteApp.onTerminate` → `ShellLog.markProcessExit("onTerminate")`
- **Why dead**: `Application.onTerminate()` is documented as "for use in emulated process environments… It will never be called on a production Android device, where processes are removed by simply killing them; no user code (including this callback) is executed when doing so." So the body never runs on any real phone, and the `======== 进程结束：onTerminate ========` marker is never written to the shared log file. The KDoc at `:73` ("Only reached in emulated processes, but it keeps the log tidy") shows the author knew — but the consequence is that `ShellLog.markProcessExit` has no reachable caller at all.
- **Reference search**: `markProcessExit|onTerminate` over `android-shell` → 4 hits, all in these two files (ZcodeRemoteApp.kt:72,74,75 and ShellLog.kt:99) → `markProcessExit` has exactly one caller and it is the never-invoked callback. `grep MainActivity|SettingsActivity|DiagReceiver|KeepAliveService|WebAppBridge|UploadSourceDialog` over `app/src/test` → 0 hits (nothing pins it).
- **Confidence**: high (mechanism), high (single-caller proof)
- **Suggested action**: delete with `ShellLog.markProcessExit` (`ShellLog.kt:99-101`); or, if the emulator path is wanted, `keep but annotate` — but then say in the KDoc that the marker can never appear in a phone-produced log.
- **Risk if removed**: removes only a log marker that is currently unreachable; the process-start banner (`ShellLog.init`, `ShellLog.kt:62-68`) still delimits sessions. Note the audit caveat: a reader of the shared log may be *expecting* a "进程结束" line — that expectation is exactly the bug.

### F3. `DiagReceiver`'s `<intent-filter>` is never consulted  [VESTIGIAL]
- **Location**: `app/src/main/AndroidManifest.xml:105-107` (receiver declared at `:101-108`)
- **Symbol**: the `com.zcode.remote.action.DIAG` intent-filter of `.DiagReceiver`
- **Why dead**: since Android 8.0 (API 26) a manifest-declared receiver cannot receive *implicit* broadcasts, and a custom action is not on the implicit-broadcast exemption list. `minSdk = 26`, so the filter can never route anything on any supported OS. Every real invocation is explicit: `am broadcast -n com.zcode.remote/.DiagReceiver -a com.zcode.remote.action.DIAG --es diag_cmd <cmd>` — and an explicit intent bypasses filters entirely. `DiagReceiver.kt:21` states this in its own KDoc: "`-n` 必带：自定义 action 的隐式广播送不到清单接收器（Android 8+ 限制）". The receiver itself stays alive (explicit broadcasts); only the filter is dead weight.
- **Reference search**: `diag_cmd|am broadcast|am start` over `android-shell` → 31 hits; **every** invocation (README.md:1003, README.md:1005, DiagReceiver.kt:18-19, tools/cdp.mjs:13-14, manifest comment `:99`) passes `-n`; no `-a`-only broadcast exists anywhere. `MainActivity.EXTRA_DIAG_CMD` (the extra that *is* needed) is read at DiagReceiver.kt:32.
- **Confidence**: high
- **Suggested action**: delete the `<intent-filter>` block only (keep `<receiver>`, keep `android:exported="true"` + `android:permission="android.permission.DUMP"`).
- **Risk if removed**: none — the documented usage keeps working. If a `-a`-only invocation is ever wanted, the filter would not have helped anyway. (Manifest may also be covered by another area's scope; recorded here because `.DiagReceiver` is one of my files.)

### F4. `WebAppBridge.config()`'s `runningSessions` payload now feeds only a log line  [VESTIGIAL]
- **Location**: `app/src/main/java/com/zcode/remote/WebAppBridge.kt:44-53` (+ `:56`), companion `core/TaskStore.kt:139`
- **Symbol**: the `sessions` map built from `ShellRuntime.store.workspaces()` / `ShellRuntime.store.runningTaskRefs()` and published as `"runningSessions"`
- **Why dead**: the payload was built so the injected layer could seed `subscribeConversationV4` before the sessions index arrives. Its only functional consumer is `zcode-protocol.js:1800-1826 RemoteClient.prototype._conversationCandidates`, whose **only** call site (`zcode-protocol.js:1882`) sits *after* `if (!CONVERSATION_SUBSCRIBE_ENABLED) return Promise.resolve();` (`:1879-1881`) with `CONVERSATION_SUBSCRIBE_ENABLED = false` (`:112`, never reassigned). So the subscription path is sealed; the only *live* read left is the wiring self-check log line `inject.js:787-788` ("原生运行集种子：N 个工作区"), which reads `cfg.runningSessions` purely to print a count. Consequence in my scope: the whole map-building loop exists to make one diagnostic number non-zero. `TaskStore.workspaces()` (`TaskStore.kt:139`) has **no other caller in the repo**.
- **Reference search**: `runningSessions|runningTaskRefs` over `android-shell` → 39 hits (Kotlin callers of `runningTaskRefs` are ShellRuntime/Tier2Probe — unrelated; the `runningSessions` *string* key appears only in WebAppBridge.kt:56, inject.js:788/797/804, tools/inject.test.js:260/263); `nativeRunningSessions` over `android-shell` → 10 hits: inject.js:797/801 (assignment from the bridge), zcode-protocol.js:1812/1813/1815 (the sealed consumer), and **tools/protocol.test.js:1045/1046/1205/1206/1211 — test-only**, where the field is set on a client object directly and `_conversationCandidates` is called directly (`protocol.test.js:1047-1048`), i.e. the tests bypass the bridge entirely and are the *only* place the seeds still do anything observable; `CONVERSATION_SUBSCRIBE_ENABLED` → 3 hits, zcode-protocol.js:112 (`= false`, never reassigned), :1879 (the guard), :2123 (comment); `_conversationCandidates` → declaration :1800 + call :1882 only; `\.workspaces\(\)|fun workspaces\(\)` → `TaskStore.kt:139` + `WebAppBridge.kt:45` only. Candidate refutations: `inject.js:787-788` is a *read*, but only of a count for a log line; `zcode-protocol.js:1812-1823` is a read, but it is behind the constant-false guard; `protocol.test.js` hits are test-only and never touch `WebAppBridge`.
- **Confidence**: medium-high (mechanism proven; the "delete" decision belongs with the JS block)
- **Suggested action**: keep but annotate **now**; delete only together with its JS companion (`inject.js:787-788`, `zcode-protocol.js:1800-1826`) — that JS block is on the brief §5 known-intentional list, so this is the Kotlin half of a deliberate keep.
- **Risk if removed**: the "接线自证" log line would permanently print `原生运行集种子：0 个工作区`, which inject.js:785-788 defines as "the native wiring is broken" — so deleting the Kotlin side alone would turn a diagnostic into a lie. Also `TaskStore.workspaces()` becomes dead the moment this block goes. On the JS side, deleting `_conversationCandidates` would break `tools/protocol.test.js:1043-1049` and `:1200-1215` (they call it directly) — so the JS half needs test edits; the Kotlin half alone breaks no test (the JS tests supply their own `config()` mock, `inject.test.js:263/283-285`).

### F5. `MainActivity`'s diag retry loop duplicates `ShellRuntime.dispatchJsDiag`  [SUPERSEDED]
- **Location**: `app/src/main/java/com/zcode/remote/MainActivity.kt:747-748` (`pendingDiag`, `diagAttempts`), `:787-807` (`tryDiag`), used from `:782-784`
- **Symbol**: `MainActivity.pendingDiag` / `diagAttempts` / `tryDiag`
- **Why dead weight**: `ShellRuntime.dispatchJsDiag(cmd, attempt)` (`ShellRuntime.kt:1257-1273`) is the same mechanism — same `window.__zcodeShellDiag && window.__zcodeShellDiag(<quoted cmd>)` payload, same "injected layer not ready yet" retry with the same budget (40 × 600 ms, cf. `LOCATE_RETRY_MS`/`MAX_LOCATE_ATTEMPTS`). It is the newer, shared implementation: `DiagReceiver.kt:40` already routes the broadcast channel through it, and its KDoc says it "沿用 MainActivity 的重试口径" (follows MainActivity's retry policy). MainActivity keeps a private copy that differs only in that it evaluates through `binding.webview.evaluateJavascript` directly, which is exactly what `ShellRuntime.evaluateJs` does — `onCreate:189` sets the evaluator to that same call. So one of the two implementations is redundant; the live one for both entry points should be `ShellRuntime.dispatchJsDiag`.
- **Reference search**: `dispatchJsDiag` over `android-shell` → 3 code hits (ShellRuntime.kt:1257 definition, :1267 self-recursion, DiagReceiver.kt:40 the only external caller); `runNativeDiag` → 4 hits (ShellRuntime.kt:1117 definition, MainActivity.kt:759, DiagReceiver.kt:39, MainActivity.kt:757 comment) — so the *native* half is already shared and only the JS-retry half is duplicated; `tryDiag|pendingDiag|diagAttempts` → MainActivity.kt only (declaration + 5 uses).
- **Confidence**: medium-high (functional equivalence is readable from source; not runtime-verified, and Gradle cannot run here)
- **Suggested action**: delete `pendingDiag`/`diagAttempts`/`tryDiag` and end `runDiagCommand` with `ShellRuntime.dispatchJsDiag(cmd)`.
- **Risk if removed**: none expected — same payload, same budget, same readiness gate (`ShellRuntime.isInjectedReady()`); the only behavioural difference is a `Diagnostics` message wording ("放弃诊断指令（注入脚本未就绪）"). Keep the `passive_on`/`passive_off` branch and its `binding.webview.reload()` (that one *is* MainActivity-specific and is the only documented foreground-channel path for those two commands, README.md:1014).
