## A. 本域功能概览（给非工程师看）

你可能同时在几个工作区里跑任务（例如 `E:\Zcode_harmony` 与默认工作区各跑一个）。桌面端允许
**同时开**多座桥，但**同一时刻只服务一座**（服务权归"最近一次订阅成功"的那座，铁证见
`docs/18` §3.3）。所以壳不能"并行跟手"，只能**主动轮换**：每隔 12 秒一拍，只对当前被服务的那座桥
发一次"重锚"（resync，逼桌面端再推一份最新进展），且只拉该桥**最饿的那一条**会话，然后换一座桥来问。
**一轮 ≤ ~9 秒，与桥数和会话数都无关**（2026-09-19 核实：代码注释口径"整轮重挂最坏 ~6s"+ 每拍重订
~3s，见 `ShellRuntime.kt:624`、`:973`）；桥数上限 5（成本取舍，不是协议限制，`Tier2Probe.kt:85
DEFAULT_MAX_COVERAGE = 5`）。你感受到的是：卡片正文每隔一阵跳一段新内容（N 座桥时单卡刷新间隔
≈ N × 12s）。

同一件事在本仓原有**两套实现，只活了一套**——现在只活着的这套还在：

1. **页面内（JS，Tier1）**：注入层在**页面自己的 socket** 上给自己开桥、自己订阅会话清单和对话流。
   2026-09-15 真机 A/B **定罪**——重复订阅把页面的接收流挤掉，卡片只剩"工作中"+转圈、内容全程不更新；
   开关 D7 已于 2026-09-17 删除。**⛔ 这套（D2 / C15 的桥路由 + 候选挑选器）已于 2026-09-18 清理
   （第 4 批，b627610）整体删除**（`docs/18` §3.9①、§4；`zcode-protocol.js` 现只保留线格式层
   `RpcFrameAssembler/RpcFrameSender/ChannelClient` 与被动旁观层 `RemoteClient.acceptObservedPayload`）。
2. **原生（Kotlin，Tier2）**：退到后台后由原生自己开一条 relay 连接，`Tier2Probe` + `BridgeManager`
   负责开桥、重锚、轮换，外加"发现链"从 `bootstrap-response.tasks` 直接读出哪些工作区有活动
   （不必再逐个打开工作区）。**这是现行唯一在跑的实现**，2026-09-17 真机验收通过（README P8、
   `docs/18` §3.8）。（2026-09-19 核实仍然成立）

第二个功能是**会话与任务索引（sessions-index）**：桌面端推来"哪些任务存在、什么状态、什么标题"的
清单。壳据此建立任务表、决定发不发通知、卡片标题写什么。这条清单断了，**通知就全瞎**
（这句原话原来写在 `zcode-protocol.js:1859-1860` 的封死块注释里，**已随第 4 批删除**；结论本身不变，
另见 `docs/18` §4 第 760 行的更正版表述）。它在两条路上各有一份解码实现：JS 一份（`zcode-protocol.js`，
被动旁观页面自己桥的帧）、Kotlin 一份（`core/SessionsIndexState.kt`，Tier2 原生桥的帧）。

数据怎么走（现行唯一活路，2026-09-19 核实行号）：

```
12s 拍（ShellRuntime 心跳泵，LIVE_PROGRESS_POLL_MS=12_000L:610 × LIVE_REANCHOR_EVERY_POLLS=1:638）
  → Tier2Probe.reanchorProgress（:235）→ RelayBridge.BridgeManager.reanchorProgress（:1040，轮换：只问"最饿的一座"）
    → BridgeSession（原生 relay 连接，:113）
      → reanchorConversationsBlocking（:433，只拉该桥最饿的一条会话，resyncConversationV4）
        → 入站帧 → SessionsIndexState（解码/重建）→ onSessionsUpdate 回调（:121，触发点 :251）
          → ShellRuntime.onSessions（:2057）→ TaskStore → 通知 / 流体云卡片
```

**D2 / C15 的那套 JS 桥管理不在这条线上（且已删除）。**

## F. 补遗（2026-09-19 新增）：sessions-index 的"防降级 stale 标记帧"规则（4c，2026-09-18 落地）

原文档未覆盖、现源码中已存在的重要机制（详 runstate.md F 节）：JS 侧 sessions-index 状态机检出
**序号缺口**那一拍，除置 `stale=true` 外还会**额外发一帧"仅标记帧"**（`_emitSessionsStale`，
`zcode-protocol.js:1226`，`stale:true, staleOnly:true`，其携带的 `sessions` 是冻结旧读数、**不许落地**）；

由 `TaskStore` 的 `staleSince` + 可信窗口（`STALE_TRUST_WINDOW_MS = 120_000L`，约 2 分钟，
`TaskStore.kt:878`）武装 `guardStaleDowngrade`（卡片/运行态不降级）与 `staleGateHold`（提前接管闸门）
两条保护。整表帧（`stale:false, staleOnly:false`）照常落地并解除陈旧标记。这条规则**替代了**原 D2
死段里"缺口后靠 `needsResync` 拉回"的旧设计，是删除 D2 的前提性补偿。
