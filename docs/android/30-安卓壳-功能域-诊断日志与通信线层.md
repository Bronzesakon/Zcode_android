## A. 本域功能概览（给非工程师看）

这个壳**没法在电脑上跑**——它做的事情（往网页里塞脚本、hook 网页的 WebSocket、在后台替网页发心跳）只有真机上才成立。所以"这个壳到底干了什么、有没有添乱"这件事，只能靠两条腿走路：一是**壳自己写一份日志文件**，二是**留一组 adb 命令**，让排查的人能随时命令壳"现在把现场报给我"。

于是有三块功能：

1. **诊断与日志**。壳把每一件值得记的事（页面加载、注入是否装上、后台心跳、崩溃堆栈）同时写到三个地方：adb 的 logcat、内存里的最近 400 行（设置页立刻能看）、以及**外部存储上的一个日志文件**。日志文件是关键——进程被系统杀掉时 logcat 的缓冲区一起消失，只有文件留得下来，所以"退到后台 30 分钟里连接还在不在"这个问题，事后只能从文件里读。设置里「诊断（真机调试）」那一页就是给人看这份日志、并把它分享出来的。另外还有一组命令：`vitals`（页面体征）、`stall_state`（承载现场）、`net_probe`（原生直接测网）等等，共十几条，是排查时唯一的"问诊"手段。

   ```
   adb 命令 ──┬─→ 原生自己处理（16 条：tier2_* / carrier_* / nudge_* / wvdebug_* …）
              └─→ 转给网页里的注入脚本（vitals / bg_state / kick_test …）
                        ↓
              网页回话 ──→ Diagnostics 内存缓冲 ──→ 设置页显示 / 复制 / 分享
                        └─→ ShellLog 文件（含崩溃堆栈，进程被杀也留得下）
   ```

2. **与桌面端的通信线层**。壳（或网页）与桌面端之间传的不是裸消息，而是**信封**：一条大消息被切成若干片、每片 base64 编码、带一个校验和与序号，收齐了才交付；收到完整一条要回一个"回执"（ack），否则桌面端会认为这条没送到、越积越多，最后把整条桥判成故障。这一层是"通知卡片能不能拿到任务进展"的物理基础——README「实现要点 2」讲的就是：通知要用的数据不在明面的 relay 载荷里，而是**再往里一层**藏在这个信封里。

3. **网页注入就绪**。注入脚本必须在**三个独立时刻**都尝试安装（页面开始加载前、页面开始加载时、页面加载完成时；`MainActivity.kt:83` 注释，2026-09-19 核实仍然成立），因为只要漏掉一次加载，整个壳就等于不存在（README「已知问题 F」）。"装上了没有"这个状态被记在一个标志位里——原 `ShellRuntime.injectedReady`，**2026-09-18 起抽成可单测的 `core/InjectionReadiness`**（由 `ShellRuntime` 持有唯一实例），诊断队列和设置页都靠它判断"现在能不能给页面发命令"。G2 修复前它的复位路径是断的（见 C14），现已接回。

**这三块的关系**：通信线层是"路"，网页注入是"车能不能上路"，诊断与日志是"路上的摄像头"。本次 5 条候选全部落在**脚手架**上——没有一条是功能本体。

### C8. 与桌面端的通信线层 —— 入站重组里"收到的是回执"这条防御分支 [`C 级`]

> ⛔ 已于 2026-09-18 清理（b627610 第 2 批，按本节建议"直接删"执行）：`RelayWire.FrameAssembler.accept()` 的 `"rpc-frame-ack" -> return null` 分支已删，现在的分流只剩 `"rpc-frame" -> Unit` / `else -> return null`（`RelayWire.kt:412-415`），守卫与文档不变（bridgeSessionId 守卫 `:411`，KDoc `:406-409`）。**JS 半边未动**（`zcode-protocol.js` 的 `if (type === 'rpc-frame-ack') return true;` 现 `:456`——它在那边是可达的，形状相同语义不同，本就明确告诫不要照抄）。以下原始分析保留存档，行号为清理前旧值。

- **功能归属**：与桌面端的通信线层。
- **这个功能是干什么的**：见 A.2。用一个具体场景说：桌面端有 5MB 的会话快照要发给壳，它会切成几十片、每片 base64 编码、标上校验和与序号，一条条发过来；壳这一侧 `RelayWire.FrameAssembler.accept()`（清理前 `RelayWire.kt:406`，现 `:410`）负责判断"这片是不是我这座桥的、是不是我要的信封类型、到齐了没有、校验和对不对"，到齐了才交给上层并回一个**回执**（`RelayBridge.sendAck`，清理前 `:156`，现 `:154`）。`sendAck` 的注释（清理前 `:157-164`，现 `:155-166`，45s 判故障的推理原文未动）记录了不送回执的真实后果：桌面端的重发缓冲会持续累积，约 45 秒后把整座桥判为故障，此后所有请求都不再应答——真机连续三天看到的"新桥好一分钟就集体超时"就是它。所以回执这条线是**活的、承重的**；被判死的只是"收到别人发来的回执该怎么办"这一行。
- **这条代码的角色**：清理前 `RelayWire.kt:406-412` 是 `accept()` 的第一道门，按信封自带类型字段分流：

  ```
  "rpc-frame-ack" -> return null     // C8：本行不可达（已删，2026-09-18）
  "rpc-frame"     -> Unit            // 继续往下重组
  else            -> return null
  ```

  `"rpc-frame-ack" -> return null` 的语义是"如果来的是回执，我就不管"。**它不可达**：唯一调用方 `RelayBridge` 的 `acceptBridgePayload()`（现 `RelayBridge.kt:141-152`）自己先判过一遍类型，只有 `zcode_type == "rpc-frame"` 才会调 `accept()`（现 `:145-147`），所以进到 `accept()` 时那个字段**必然**是 `"rpc-frame"`，永远匹配不到 ack 那一行。（2026-09-19 核实：外层过滤结构未变。）
- **一个必须说清的细节（比第一阶段结论更进一步）**：这个 `when` 里的**另外两条分支同样两头都够不着**，而且其中一条**看上去有测试、其实没有**：
  - `else -> return null`（清理前 `:411`，现仍在 `:414`）：生产到不了（外层已过滤）。测试里有一条**名字像是冲着它去的**——`RelayWireTest.kt:151-156` 的 `foreign bridge and non-frame payloads are ignored`，其中 `:155` 断言 `accept(JSONObject().put("zcode_type", "workspace-bridge-ready"))` 返回 null。**但这条断言并没有走到 `else`**：它构造的 JSON 里**没有 `bridgeSessionId`**，而 `accept()` 的第一道守卫（现 `:411`）`if (payload.optString("bridgeSessionId") != bridgeSessionId) return null` —— 空串 ≠ `"bridge-1"`，函数在**进入 `when` 之前就返回了**。所以这条测试实际验证的是"外来桥/缺字段的载荷被忽略"，**不是**"类型不符的载荷被忽略"。这算一处测试覆盖的假象（值得单独记一笔），但不影响本轮建议。【2026-09-19 核实：该测试仍未补 `bridgeSessionId`，覆盖假象仍在；C8 分支本身已删，`else` 成了类型不符的唯一落点。】
  - `"rpc-frame-ack" -> return null`：生产到不了，测试也到不了（全仓 grep `rpc-frame-ack` 在 `app/src/test` 零命中）→ **已于 2026-09-18 删除**。

⇒ 如果只是把 `runDiagCommand` 的尾部换成 `ShellRuntime.dispatchJsDiag(cmd)`，那么**冷启动（`am force-stop` 后 `am start -a …DIAG`）这条路径的第一条命令会在 `:188` 被直接丢弃**，只留下 `诊断指令无处执行（JS 求值通道未就绪）` 一行。**而"冷启动时注入脚本还没就绪"正是这套队列存在的唯一理由**——这会让 C14 的合并在它最该起作用的那条路径上反过来变成功能回归。
修法（一行）：把 `:189` 的 `setJsEvaluator` 挪到 `:188` 之前，或让 `dispatchJsDiag` 在 `jsEvaluator == null` 时也走重试分支。**这一步必须与合并同批做。**
